# PawPi Pre-Launch Night Run (2026-08-16) — QA & Hardening · Performance · Legal · Apple submission prep

**Designed in Cowork:** 2026-08-15 · One autonomous Claude Code run, four sequential phases
(A → B → C → D). Each finding/optimization/doc is its own PR: CI-green → merge → deploy → log.
**Live DB is at migration 0110 — next number 0111.** Standing rules apply: no fake/mock data (empty
states only); EN+ES on every user-facing surface; pet_id + owner_user_id scoping; additive numbered
migrations each with verify_XXXX.sql; own-row/household RLS; app runs as pawpi_app; never break prod
(degrade cleanly); celebrate the dog/family, never shame; keep docs current (Rule 6).

## Honest scope (what this run can and cannot do)

- **CC cannot tap a real device / see screens.** The "act like a person" QA is realized as (1) an
  end-to-end journey test through the real backend, (2) systematic code audits for the issue classes
  below, (3) fixes + deploys. Anything that truly needs eyes-on-device is logged as an **ON-DEVICE PUNCH
  LIST** for Tats, not silently skipped.
- **CC does NOT submit to Apple.** It builds a submission-READY state + a step-by-step runbook Tats runs
  with their (already enrolled) Apple credentials. CC never presses Submit.
- **Legal docs are drafted, NOT legally reviewed.** Every legal deliverable is stamped "DRAFT — needs a
  lawyer's review before launch; not legal advice."
- **Perf telemetry = Railway metrics + Postgres EXPLAIN/ANALYZE** (no external Grafana wiring assumed).

## PHASE A — QA & Hardening sweep

**A1 — End-to-end journey (act like a real user).** First check for an existing e2e/device harness
(Detox / Maestro / Playwright / an Expo-web target). If a drivable target exists, drive the real flows
headless; otherwise build a comprehensive **API-level integration journey test** that mimics the full
lifecycle against real Postgres: sign up → onboarding (first moment, welcome paw, birthday/gotcha) →
create pet → set reminders (feeding / walk / meds / photo check) → post a daily moment → give/receive
paws → invite + accept a caregiver → book a provider → cancel the booking → weekly digest / streak →
delete account. Every step that errors or misbehaves is a finding; fix the backend bugs.

**A2 — The specific bugs Tats already found (do these for sure):**
- **Fake/demo data leaking into production.** A demo pet **"Mango"** (and any seeded demo posts/content)
  is visible in prod feeds/discovery — a direct no-fake-data violation. Find where demo/seed data is
  created and how it reaches prod; **guard all demo/seed content out of production** (env/flag) and
  remove the leaked rows **safely** (soft-remove/guard, not a reckless prod delete — log exactly what
  was removed). Empty states instead.
- **Stale relative timestamps.** Posts show "just now" when they're old (e.g. Mango's post). Fix the
  relative-time formatter (correct reference time / timezone / no cached "now") so timestamps are honest
  everywhere they render.
- **Navigation "layers on top of layers."** Search/Discovery opens as a stacked layer (not a pushed
  screen); tapping a pet stacks another layer; tapping a photo stacks another — leaving modal-on-modal-
  on-modal, dismissible only by swipe/back. Audit expo-router usage (`presentation: 'modal'` vs card
  push, nested navigators). Refactor Discovery → pet profile → photo so they **push as real screens with
  a proper back stack** (or at minimum never stack a modal on a modal). Flag ON-DEVICE PUNCH LIST for
  the final feel.

**A3 — Systematic audits (each finding → fix or punch-list):**
- **Every interactive control.** Inventory buttons/taps across the main screens: does it work, what's it
  for, is it necessary? Fix dead/no-op handlers + broken nav targets; flag redundant/confusing controls
  for a keep/remove decision. Put the inventory in the report.
- **Moderation / policy affordances (Apple-critical).** Do BOTH posts AND comments have a **Report**
  action, plus **block/hide user** and a way to delete your own content? Cross-check the UGC moderation
  policy (`docs/phase-ugc-moderation-plan.md`, `docs/ugc-moderation-build-log.md`). Apple 1.2 requires
  report + block for UGC. Add any missing affordance; wire it to the real moderation backend.
- **Responsive / visibility (code-level).** Audit for hardcoded sizes, text overflow/truncation,
  safe-area handling, small-screen (iPhone SE) vs large, and accessibility labels/contrast. Fix obvious
  code issues; punch-list the purely visual ones.
- **Empty states + i18n parity.** Every surface has an honest empty state and full EN+ES parity.

**A4 — Abuse / security hardening (defensive, not malicious).** In tests, attempt IDOR / cross-user /
cross-pet / cross-business access and verify RLS/authz **deny**; check write endpoints for authz, input
validation, and basic rate-limiting; confirm the new `biz_*` notify + caregiver paths don't leak across
tenants. Fix gaps; prove with harness tests. Do NOT perform destructive attacks on prod data.

## PHASE B — Performance (retention-critical speed)

Profile the hot, retention-critical paths with **EXPLAIN/ANALYZE + index audits + Railway metrics**:
feed load, discovery, Health→Today, notifications/bell, bookings, day-card grouping, weekly-digest.
Find N+1s in API routes and missing/!used indexes (especially the pet_id/owner_user_id scoped queries,
the `biz_*` notify resolver, feed ordering, caregiver access joins). Ship additive **index migrations
(0111+) + query rewrites**, each with **before/after timing evidence** in the report. Prioritize app-open
and feed latency. Add cheap slow-query logging if trivial; note anything that would need real Grafana/
observability wiring as a follow-up. Each optimization = its own PR, verify, deploy, log.

---

## PHASE C — Legal: Privacy Policy + Terms & Conditions (EN + ES, detailed)

Audit what PawPi now actually collects/processes (from schema + features): account + email + auth; pet
profiles + **health/medical data**; **location** (walks, neighborhood/coarse geo); photos + social
content; **caregivers / shared custody**; **push tokens + notifications**; **payments/orders**; adoption
applications; usage/analytics; third parties/subprocessors (Supabase, Railway, Expo push, the payment
processor, email sender). Then rewrite the in-repo legal docs under `docs/legal/` (and the hosted/linked
versions the app's Settings point to) in **EN + ES**, detailed:
- **Privacy Policy:** data collected + purposes; legal bases; sharing + subprocessors; **health-data**
  and **location** handling; retention; user rights (access/**delete account** — the flow exists);
  minors; international transfer; security; contact.
- **Terms & Conditions:** acceptable use; **UGC + moderation** (report/block, zero-tolerance for abuse —
  Apple-aligned); provider/business terms; payments/refunds; disclaimers (**health copy is not
  diagnostic**); liability; termination; governing law.
Stamp both **"DRAFT — needs a lawyer's review before launch; not legal advice."** Ensure they're
reachable from in-app Settings AND available at a hosted URL for the App Store privacy link. These feed
the Phase D App Privacy questionnaire.

## PHASE D — Apple submission prep (build to `eas submit`-ready + runbook)

Apple account is **enrolled + credentials ready**, so prepare everything up to the manual console steps:
- **Config:** finalize `app.json` / `eas.json` — bundle id, version + **buildNumber bump**, all
  **permission usage strings** (location / notifications / camera / photos / health if used) in EN+ES and
  consistent with the App Privacy map; icons/splash present. Wire an **EAS `production` build + submit
  profile** (with `appleId` / `ascAppId` / `appleTeamId` placeholders for Tats) so `eas build -p ios
  --profile production` and `eas submit -p ios` are runnable by Tats. Include the **APNs/push credential**
  setup (from BN2's night-run notes) so iOS push lights up.
- **Store content:** generate EN+ES **App Store metadata** (name, subtitle, promo text, description,
  keywords) from `docs/app-store-connect-content.md`; the **App Privacy "nutrition label" data map**
  derived from Phase C; **screenshot spec** (required sizes) — generate screenshots if a harness exists,
  else spec them for Tats. Cross-check `docs/app-store-readiness.md` + `docs/guideline-1.2-audit.md`.
- **Runbook:** write `docs/app-store-submission-runbook.md` — every manual App Store Connect step in
  order (create app record → set privacy-policy URL → fill App Privacy → upload build → attach metadata +
  screenshots → export-compliance → submit for review), plus the exact `eas` commands Tats runs locally.
  **CC must NOT attempt to submit** (no Apple login in its env).

## Guardrails / stop conditions

- Each fix/optimization/doc = its own PR: CI-green → merge (merge commit + delete branch) → apply any
  migration + verify + Railway healthy (if this env can't apply DDL, log "0111+ awaits hand-apply" +
  degrade cleanly) → log to the report + `docs/night-run-log.md` + `docs/roadmap.md`.
- Streams/items are independent — if one can't go green after real effort, write a **BLOCKED** entry and
  move on (don't stall the whole run).
- **Never:** submit to Apple; hard-delete prod user data; widen RLS beyond the established model; ship
  fake data; break EN+ES parity.
- CLOSE: write a top-of-report **executive summary** — what shipped, the ON-DEVICE PUNCH LIST, the
  legal-review checklist, and the exact Apple runbook next-steps for Tats. Refresh the
  `PawPi_instructions.md` snapshot.
