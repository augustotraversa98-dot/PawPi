# Build Plan — Guideline 1.2 UGC Moderation (minimum to pass review)

**Goal:** ship the four Apple Guideline 1.2 safeguards + contact info at the **minimum** bar to pass
review — nothing gold-plated. Source gap report: [`docs/guideline-1.2-audit.md`](guideline-1.2-audit.md).

**Status:** PLAN ONLY — nothing implemented yet.

**The five required outcomes**
- **(A)** EULA acceptance gate at signup (terms checkbox, web + mobile) + zero-tolerance language in the Terms.
- **(B)** Content filter — profanity/word-list text filter on submit across UGC text surfaces. **No ML / NSFW image moderation in v1** (explicit fast-follow, see Deferred).
- **(C)** Report/flag — one polymorphic `content_reports` table + a reusable report action on every UGC surface; reported content hide/removable **by us** with a 24h handling path.
- **(D)** Block — a real `user_blocks` table + enforcement (blocked users' content hidden, interaction prevented), distinct from the friend-request `'blocked'` state.
- **Contact** — wire the dead "Contact Us" row + the empty legal URLs.

**House rules honored:** ONE migration, **`0065`** (next after `0064`). All new tables `ENABLE`+`FORCE`
ROW LEVEL SECURITY, `owner_user_id`/actor = `user_profiles.id` (resolved from `auth_user_id`), integer
`generated by default as identity` PKs, soft-delete via `deleted_at`. Controlled/cross-author writes go
through `SECURITY DEFINER` helpers granted to `pawpi_app` (the `0044 app_notify` / `0047 forum_vote`
pattern). New tables registered in the completeness guard
(`anything/apps/web/test/integration/rls-gap-closure.integration.test.ts`). Migration is
harness-proven first, hand-applied to Supabase after merge (test-backlog ACTION 1).

### T1 — Migration `0065`: moderation primitives (DB only, no app code)

**Context.** Land every DB change for 1.2 in the single allowed migration. No routes, no UI — this PR
is provable entirely in the integration harness as `pawpi_app`.

**Surfaces touched.** None at runtime; adds columns to the peer-UGC content tables.

**DB changes (`supabase/migrations/0065_ugc_moderation.sql`):**
- **`content_reports`** — polymorphic report ledger.
  - `id` int identity PK · `reporter_user_id int not null references user_profiles(id) on delete cascade`
    · `target_type text not null` CHECK in
    `('post','bark','forum_thread','forum_comment','dm_message','provider_message','review','pet_profile','user_profile','adoption_listing','event','social_walk','lost_report')`
    · `target_id int not null` · `reason text` (CHECK against a small enum: `spam`, `harassment`,
    `hate`, `sexual`, `violence`, `other`) · `details text` · `status text not null default 'open'`
    CHECK `('open','actioned','dismissed')` · `created_at`/`updated_at` · `deleted_at`.
  - Index `(target_type, target_id)`, `(status, created_at)`, `(reporter_user_id)`.
  - RLS: SELECT/own (`reporter_user_id = current_app_user_id()`); INSERT with check
    `reporter_user_id = current_app_user_id()`; **no** UPDATE/DELETE policy (status changes only via the
    admin DEFINER helper below).
- **`user_blocks`** — real user-to-user block (distinct from `pet_friendships.status='blocked'`).
  - `id` int identity PK · `blocker_user_id int not null references user_profiles(id) on delete cascade`
    · `blocked_user_id int not null references user_profiles(id) on delete cascade` · `created_at` ·
    `deleted_at`. Partial unique index `(blocker_user_id, blocked_user_id) WHERE deleted_at is null`.
    CHECK `blocker_user_id <> blocked_user_id`.
  - RLS: SELECT/own (`blocker_user_id = current_app_user_id()`); INSERT with check
    `blocker_user_id = current_app_user_id()`; UPDATE/DELETE own (for unblock = soft-delete).
- **`hidden_at timestamptz`** (additive, nullable) on the peer-UGC content tables that can be moderated:
  `posts`, `post_barks`, `forum_threads`, `forum_comments`, `messages`, `dm_messages`,
  `provider_reviews`, `adoptable_listings`, `events`, `social_walks`, `lost_reports`. Distinct from
  author `deleted_at` — `hidden_at` = "removed by us."
- **`banned_at timestamptz`** (additive) on `user_profiles` (eject an abusive user).
- **DEFINER helpers** (pinned `search_path`, `grant execute … to pawpi_app`):
  - `app_is_admin()` → `current_app_user_id()`'s `user_profiles.role = 'admin'` (role already in the
    `valid_role` CHECK).
  - `app_moderate_hide(p_target_type text, p_target_id int)` / `app_moderate_unhide(...)` — set/clear
    `hidden_at` on the right table; raise unless `app_is_admin()`. Marks the matching `content_reports`
    rows `status='actioned'`.
  - `app_ban_user(p_user_id int)` — set `banned_at`; admin-only. (Sign-in block enforced in T5/auth.)
  - `app_user_is_blocked(p_a int, p_b int) returns boolean` — either-direction live block exists
    (read helper for T3).
- Widen `notifications_type_check` (additively, the `0051` pattern) for a `'report_received'` type
  (admin ping) — optional; include only if trivial.
- Register all new/changed tables in the completeness guard.

**Acceptance criteria.**
- `content_reports` + `user_blocks` are FORCE-RLS; a `pawpi_app` user can insert only their own
  report/block and read only their own rows; cross-user read denied.
- Non-admin cannot set `hidden_at`/`banned_at`; `app_moderate_hide` as admin hides the target;
  `app_user_is_blocked` returns true both directions.
- Migration is idempotent (re-runs clean) and the gap-closure completeness guard passes.

**Device/test note.** Pure DB. Add `test/integration/ugc-moderation.integration.test.ts` (real Postgres,
runs as `pawpi_app`). No device test. Unit gate unchanged; integration count grows.

**Required to pass review:** YES. **Size: M.**

### T2 — Report / Block / admin-action APIs (backend, no UI)

**Context.** Thin routes over T1's tables/helpers. Provable with vitest + curl, no UI.

**Surfaces touched.** New API routes only.

**DB changes.** None (uses T1).

**Routes (`anything/apps/web/src/app/api`):**
- `POST /api/reports` — `{ target_type, target_id, reason, details }` → insert (RLS pins reporter).
  `GET /api/reports` — caller's own reports (idempotency / "already reported").
- `POST /api/blocks` `{ blocked_user_id }` · `DELETE /api/blocks/[id]` (soft-delete unblock) ·
  `GET /api/blocks` — my block list.
- `GET /api/admin/reports` (open queue) + `POST /api/admin/reports/[id]/action`
  `{ action: 'hide'|'remove'|'dismiss', ban?: boolean }` → calls `app_moderate_hide` / `app_ban_user`;
  gated by `app_is_admin()`. **Minimal** admin surface — a JSON queue, not a dashboard.

**Acceptance criteria.**
- Reporting twice is idempotent/no-op-safe; reporting requires auth; bad `target_type` → 400.
- Block/unblock round-trips; non-admin hitting `/api/admin/*` → 403.
- Admin "hide" sets `hidden_at` and flips the report to `actioned`; "remove"+ban also sets `banned_at`.

**Device/test note.** vitest route tests + manual curl. No device test.

**Required to pass review:** YES (this is the mechanism Apple checks for, minus UI). **Size: M.**

### T3 — Enforcement in read paths (hidden + blocked filtering)

**Context.** Make hide and block actually do something. Highest-risk ticket (touches many read routes) —
isolated so it can be tested on its own.

**Surfaces touched (read routes):** feed `posts/route.js` + `posts/[id]`, `posts/[id]/barks`,
`forum/threads` + `forum/threads/[id]/comments`, `dm-threads/[id]/messages` + `threads/[id]/messages`,
`search/route.js`, `social-walks/route.js` (discovery), `providers/[id]/reviews`, `events/route.js`,
`lost-reports/route.js`, `pets/[id]/profile` (hide a banned/blocked author's content).

**DB changes.** None.

**Rules.**
- Every list/detail read adds `AND hidden_at IS NULL` (alongside existing `deleted_at IS NULL`).
- Every feed/discovery/thread/DM read excludes content authored by users in an either-direction
  `user_blocks` relation with the caller (reuse `app_user_is_blocked` or a shared SQL clause).
- Blocked-pair interaction prevented: DM send / bark / reply to a blocking-or-blocked user → 403.

**Acceptance criteria.**
- A hidden post/bark/thread/comment/review/etc. disappears from its list and 404s on detail.
- After A blocks B: B's posts/barks/forum/walks vanish from A's views and vice-versa; neither can DM the
  other; existing threads stop accepting new messages between them.

**Device/test note.** Integration tests per surface (two-user fixtures). Smoke on device: block a second
test account, confirm their feed/forum/DM content disappears.

**Required to pass review:** YES (without this, (D) is cosmetic). **Size: M–L.**

### T4 — Report + Block UI actions (mobile, one shared component pair)

**Context.** One `<ReportAction>` + `<BlockAction>` (confirm sheet → T2 APIs), dropped into each
surface's overflow/`···` menu. Build the components once; wiring per surface is mechanical.

**Surfaces touched (mobile):** Feed `PostDetailModal.jsx` + feed cards (post + bark), `forum-thread.jsx`
(thread + comment), `messages.jsx`/`chat.jsx` (DM thread header → block; long-press message → report),
`pet-profile.jsx` + user profile (block user / report profile), `service/provider.jsx` (report review),
`service/adoption.jsx` (report listing), `events.jsx` (report event), `nearby-walks.jsx` (report walk).

**DB changes.** None.

**Acceptance criteria.**
- Every UGC surface listed exposes Report (and Block where an author is shown) in its menu.
- Report shows reason picker → success toast; double-report is a no-op.
- Block shows confirm → on success the blocked user's content is gone on next fetch (relies on T3).
- Own content shows Delete (existing), not Report.

**Device/test note.** Per-surface jest component tests for the shared actions. **Device pass required:**
walk each surface, report + block with a second test account, confirm content drops.

**Required to pass review:** YES. **Size: M–L** (breadth, but repetitive).

### T5 — EULA acceptance gate + zero-tolerance Terms

**Context.** The real signup surface is the web Auth.js page rendered in the mobile WebView, so the
gate must live there; add a matching gate on the Expo-web/native entry for completeness.

**Surfaces touched.** Web `account/signup/page.jsx`; mobile `welcome.jsx` / `onboarding.jsx`;
`docs/legal/terms-of-service.md`.

**DB changes.** None required. (Optional `user_profiles.terms_accepted_at` audit column — if wanted,
fold into `0065`; it is **not** required for approval — see Deferred.)

**Work.**
- Web signup: required, unchecked-by-default checkbox — *"I agree to the Terms of Service and Privacy
  Policy"* with live links — that disables submit until checked.
- Mobile welcome/onboarding: same required checkbox on the account-creation path (replaces today's
  passive `welcome.jsx:159–181` line).
- Add a **zero-tolerance** clause to the Terms: explicit no-tolerance stance on objectionable content
  and abusive users, that reports are reviewed and acted on within 24h, and that violators' content is
  removed and accounts ejected.

**Acceptance criteria.**
- Cannot create an account (web or mobile path) without checking the box.
- Terms text contains the zero-tolerance / objectionable-content / abusive-user language.

**Device/test note.** Web: submit blocked until checked. Device: signup flow blocks until accepted.

**Required to pass review:** YES. **Size: S–M.**

### T7 — Text content filter on submit (profanity/word-list)

**Context.** Apple's "method to filter objectionable content." Minimum = a shared server-side text
filter at the write chokepoints. No image moderation in v1.

**Surfaces touched (write routes):** `posts`, `posts/[id]/barks`, `forum/threads` +
`forum/threads/[id]/comments`, `dm-threads/[id]/messages` + `threads/[id]/messages`,
`providers/[id]/reviews`, `user-profile`, `pets` (name/bio), `adoption/listings`, `events`,
`social-walks`, `lost-reports`.

**DB changes.** None (rejects at the route; or sets `hidden_at` to hold — reuses T1).

**Work.**
- One shared `moderateText(text)` util (word-list/profanity, normalized for leetspeak/spacing) in
  `api/utils/`. On match: reject with 422 (or auto-`hidden_at` + report for borderline) — pick reject
  for v1 simplicity.
- Apply at each write route before insert.

**Acceptance criteria.**
- Submitting flagged text to any listed surface is rejected (or held); clean text passes unchanged.
- Unit tests on the filter (positives, negatives, evasion); route tests on 2–3 representative surfaces.

**Device/test note.** Device: post known-bad text on one surface, confirm rejection copy.

**Required to pass review:** YES. **Size: M.**
