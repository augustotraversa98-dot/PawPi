## NR1 — Quick Check: can't select a body-area status (stuck on "Eyes")

**Files:** `src/components/Health/GeneralCheck/GeneralCheckModal.jsx` (+ its data
`src/data/generalCheckData.js`, hook `src/hooks/useHealthTracking.js` `useLogGeneralCheck`).

**The actual complaint (owner, clarified):** the user is **trapped on the first body area ("Eyes") and
cannot move to the other body parts** (ears, teeth, skin, paws, face, mood, energy). PR #436 made the
status options ("Looks usual" / "Something changed") render, but **Next is a hard gate** — it only
enables after a status is chosen for the CURRENT area (`canProceed = currentAreaData.status !== null`),
and there is no other way to navigate between areas. So if the selection is fiddly or the user just wants
to jump to a different body part, they're stuck on Eyes.

**Do — two parts:**
1. **Remove the trap (primary, recommended default):** let the user move through ALL body areas freely
   instead of being blocked. Make the per-area status OPTIONAL for navigation — **Next always advances**
   (an area with no selection is simply "not checked", not an error), and/or add explicit area navigation
   (Back/Next already exist; consider a tappable area list / stepper so any of the 8 parts is reachable
   directly). Completion should save only the areas actually assessed (skip un-checked ones); never
   invent data. Drop/relax the "Choose an option to continue" hard-block accordingly.
2. **Verify selection works on device:** independently confirm on the iOS Simulator that tapping "Looks
   usual" / "Something changed" fills the radio and updates state (if it doesn't, fix the touch-delivery
   cause — candidates: `TouchableOpacity` inside this scroll/modal misbehaving → switch to `Pressable`;
   an overlapping/`pointerEvents` view from the height fix; the `KeyboardAvoidingView behavior="padding"`
   wrapper). 

VERIFY end-to-end on the Simulator: the user can move through all 8 areas (with or without selecting a
status on each), selecting a status works, and completing **persists** via `useLogGeneralCheck` (real
POST — confirm the row lands; no mock). Keep EN+ES.

**Test:** keep the jest suite green (add coverage that Next advances without a per-area selection) AND
include a Simulator verification note/screenshot in the PR.

## NR3 — Care Ring: stop the accidental/silent "All good" write

**Files:** `src/components/Health/CareRingCard.jsx` (the "✓ All good" Pressable),
`src/hooks/useHealthReinforcement.js` (`useLogAllGood`).

**Root cause (verified against prod DB, pet 18 "Soporte"):** the ONLY thing that fills the ring's "care"
segment for this owner is a `health_wellness_logs` row `check_type:"general"`, `notes:"All good ✓"` —
written by `useLogAllGood`, whose ONLY caller is the "✓ All good" Pressable's `onPress` in
`CareRingCard.jsx`. The write is **instant, silent, irreversible**, and the green "✓ All good" box sits
directly under the "Care" segment pill — trivial to mis-tap. The owner reports the segment going "done"
without intentionally tapping it. (The pet-profile ring only has *navigating* segments — not the source.)

**Do:**
1. INSTRUMENT + REPRODUCE on the Simulator: log a breadcrumb (+ stack) when `logAllGood.mutate` fires and
   run the owner's flow (tap the Care pill, open a tracker/reminder, press Back/Cancel) to catch any
   UNINTENDED trigger (event bubbling, overlapping hit target). Fix any real misfire; report it.
2. REGARDLESS, make the care log **deliberate + reversible**:
   - Require an explicit confirmation before writing (EN/ES: "Log a quick check-in for {pet}? Everything
     looks good today." → Cancel / Log). No write on a bare tap.
   - Visually separate the "All good" action from the segment pills (distinct placement/affordance) so it
     can't be mistaken for "Care"; copy makes clear it CREATES a wellness log.
   - Add undo: after logging, offer "Logged ✓ · Undo" that deletes the just-created wellness log (owner+
     pet scoped), or let tapping the filled Care segment remove today's "all good" log.
3. Keep Care Ring integrity intact; add a test that a bare press does NOT write without confirmation.
