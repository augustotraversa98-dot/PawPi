# 2.54 — Pet-insurance marketplace (new `insurance` capability)

Read `00-README.md` (Wave 6 order + the ⚡ autonomy preamble) first. Web + mobile + migration. A SPINE +
discovery play: a new `insurance` capability whose providers list plans an owner can browse, compare, and
request a quote on (lead capture). v1 is a MARKETPLACE / lead-gen — NOT real underwriting or in-app
binding/payment. Reuse the provider spine, discovery, and the storefront (2.22); do NOT rebuild them.

```
ORIENTATION
Read ARCHITECTURE.md and supabase/SCHEMA_NOTES.md to get oriented, then this task. PawPi Expo mobile +
web API. Phase-2 ticket 2.54: a pet-insurance marketplace as a new `insurance` capability on the existing
provider spine. Read docs/phase2-tickets/00-README.md (CORE MODEL: gate on a CAPABILITY via
requireProviderCapability, NEVER on provider_type; shared conventions; the Wave 5 autonomy preamble).
AUTONOMY: don't ask; pick the sensible, on-brand option and proceed. CI green → auto squash-merge; red →
fix then merge. One fresh branch off origin/main: ticket/insurance-marketplace.
Gates: npm test (web vitest + mobile jest); npm run test:integration (real-Postgres RLS).

CONTEXT
- The MULTI-CAPABILITY model (2.1): add `insurance` to ALLOWED_CAPABILITIES (the CHECK that lists
  capabilities — widen it additively, same drop+re-add pattern used to add 'telehealth' in 0040). A
  provider holding `insurance` appears under that capability in discovery (?type=insurance).
- The provider storefront (2.22: cover + bio + links + posts) and provider_services already exist. Plans
  are best modeled as a dedicated insurance_plans module (richer than a generic service) but should render
  through the SAME storefront surface an owner already knows.
- Payments/underwriting are NOT in scope: v1 captures a LEAD (the owner expresses interest / requests a
  quote) and routes it to the insurer; binding happens off-platform. Note in-app checkout as a follow-up
  (reuses 2.3 if ever wanted).
- No medical data flows to insurers in v1 beyond what the owner explicitly puts in a quote request (pet
  species/breed/age + optional notes). Do NOT auto-attach the Vet Record.

GOAL
An insurer/broker (provider with the `insurance` capability) publishes plans (name, tier, monthly price
range, species, coverage highlights, deductible/reimbursement notes, link to full terms). An owner browses
the insurance marketplace, compares plans side-by-side, and submits a quote/interest request for a
specific pet; the insurer sees the lead in their dashboard and follows up. Real data + empty states only.

SCOPE
- Migration (next free ≥0054 — check supabase/migrations/ at build time; expected 0054). FIRST widen the
  capabilities CHECK additively to include 'insurance' (drop+re-add, like 0040 added 'telehealth'). Then:
  insurance_plans (id, provider_id, name, tier text nullable, species text nullable, monthly_price_min
  numeric nullable, monthly_price_max numeric nullable, deductible text nullable, reimbursement text
  nullable, coverage_highlights text[] default '{}', exclusions text nullable, terms_url text nullable,
  published bool default false, created_at, updated_at).
  insurance_leads (id, plan_id nullable, provider_id, owner_user_id, pet_id nullable, pet_species text
  nullable, pet_breed text nullable, pet_age text nullable, contact_email text nullable, contact_phone
  text nullable, note text, status text ['new','contacted','closed'] default 'new', created_at).
  ENABLE+FORCE RLS:
    • insurance_plans: PUBLISHED plans are any-authed READ (public marketplace); active provider STAFF of
      provider_id write/read-all (incl. unpublished) — model on provider_services (0024): admin/staff
      write, published public read. Reuse app_is_active_staff_of / app_is_provider_admin.
    • insurance_leads: the OWNER reads/creates own leads; the target provider's active STAFF read + update
      the status of leads for THEIR provider; deny-by-default; no cross-provider leakage. (Owner-or-
      provider-scoped, like a booking.)
  Harness proofs: published plan any-authed read / unpublished only provider staff; owner creates + reads
  own lead; the provider's staff read + status-update their leads; other-provider staff + outsiders get
  zero on leads; owner can't edit a plan; non-staff can't publish. Flag in docs/test-backlog.md ACTION 1.
- Web (provider dashboard, reuse the shell): an Insurance/Plans editor (create/edit/publish/unpublish
  plans with coverage highlights + terms link) + a Leads inbox (list with pet/contact/note + status
  update). Capability-gated (only providers holding `insurance`). NO new shell.
- Mobile (owner-facing): an Insurance entry under Services → discovery filtered to `insurance` providers →
  a marketplace list of published plans with a COMPARE view (side-by-side: price range, deductible,
  reimbursement, highlights) → "Get a quote" form for a chosen plan + pet (prefills species/breed/age from
  the pet; owner confirms contact) → creates a lead → confirmation. Empty states ("No plans yet" / "No
  insurers available"). No fake plans.
- Tests: web vitest (plan CRUD + publish gating to staff; published-only public read; lead create owner-
  scoped + provider status update; capability gate; cross-provider isolation); integration (insurance_plans
  + insurance_leads RLS as above proven as pawpi_app; capability CHECK widened; completeness guard green);
  mobile jest (marketplace lists published plans; compare renders; quote form posts the right body incl.
  prefilled pet fields; empty states).

DO NOT: gate on provider_type (use requireProviderCapability('insurance')); rebuild discovery/storefront/
dashboard shell (extend/reuse); build in-app binding/payment or real underwriting (lead-gen only, note as
follow-up); auto-attach the Vet Record / send medical data to insurers (only what the owner enters);
expose another provider's leads; show fake plans/leads. Migrations hand-applied by Tats — flag in
test-backlog ACTION 1.

VERIFY: npm test + integration green; completeness guard green. PR body: the widened capability CHECK +
insurance_plans + insurance_leads with RLS proofs (published public read, staff write, owner-scoped leads,
cross-provider isolation), the dashboard plans+leads UI, the mobile marketplace + compare + quote flow.
DEVICE/BROWSER: as an insurer, publish 2 plans → they appear in the owner marketplace; compare them; submit
a quote for a pet → the insurer sees the lead + updates its status; unpublished plans stay hidden; another
insurer never sees the lead; empty marketplace shows the empty state.
```
