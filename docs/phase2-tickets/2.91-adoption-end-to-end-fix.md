# 2.91 — Adoption end-to-end fix: business can edit + see its images/info, and pet owners actually see listings

**Status:** ready · **investigate first — expected NO migration** · independent · safe-parallel: partial
(provider adoption editor + mobile adoption browse/detail)

## Context
Adoption is already substantially built — this is a FIX of existing surfaces, NOT a rebuild. Do NOT create
a new adoption table or migration. What exists:
- `adoptable_listings` table, migration **0038** — includes `photo_urls text[]` + `video_url text`; RLS +
  the `adoption` capability gate.
- Provider editor `anything/apps/web/src/app/provider/components/ProviderAdoption.jsx` — create form with
  photo/video upload and a per-listing **Media** editor (`ListingMediaModal`) saving via
  `useUpdateAdoptableListing` PATCH (ticket 2.85, shipped).
- Pet-owner side: adoption browse (ticket 2.86) + adoption detail page (ticket 2.87) on mobile
  (`service/adoption.jsx` + its detail screen).

## Current issue (reported on device by Tats)
After a business uploads an adoption listing: (a) it **can't edit** the listing afterward, (b) it **can't
see the images it uploaded**, (c) it **can't see the info it wrote** about the animal, and (d) the listing
is **not displayed to pet owners at all**. Given the infra above already exists, these are wiring /
prefill / read-back / regression bugs — find and fix each.

## Expected behavior
1. **Business can EDIT an existing listing.** Opening a saved listing in the provider editor prefills every
   field it was saved with (name/info text, status, and the uploaded photos + video) so the business can
   review and change what it posted, and re-save persists the edits (via the existing
   `useUpdateAdoptableListing` PATCH — reuse, don't add a new route).
2. **Business can SEE its images + info read back.** The listing list/editor shows the cover + all uploaded
   photos and the written info for each listing (not a blank form, not a missing thumbnail).
3. **Pet owners SEE adoption listings.** The mobile adoption browse (2.86) lists real published/available
   listings from `adoptable_listings`, and the detail page (2.87) shows the photos, video, and info. Trace
   why it currently shows nothing (e.g. the list query, the capability/status filter, an empty-state that
   masks real data, or a broken route) and fix it. Real data only — empty state only when truly empty.
4. Media continues to flow through the existing Storage upload path + shared `ImageUploader` /
   `VideoUploader` (no new upload path).

## Data / API rules
Expected **no migration** — `adoptable_listings` (0038) already has the needed columns. Only if you find a
genuinely missing column after investigating, add it as an additive migration at the next free number and
FLAG it in `docs/test-backlog.md` ACTION 1 (do not duplicate the table). No RLS loosening — reuse the
existing 0038 provider-admin write / public-read-of-available posture; if you add a read route, prove it in
the integration harness. Adoption public reads must expose only listing/animal fields, never provider-
private data.
