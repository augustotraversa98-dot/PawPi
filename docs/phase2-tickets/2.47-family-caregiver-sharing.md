# 2.47 — Family & caregiver sharing (scoped, revocable pet access between people)

Read `00-README.md` (Wave 5 autonomy preamble) first. Web + mobile. EPIC feature E2. Reuses the consent
engine pattern (care_access_grants) but for PERSON↔PERSON. New table → migration.

```
ORIENTATION
PawPi Expo mobile + web API. Phase-2 ticket 2.47: let an owner share a pet with another PERSON — a family
member (full co-management) or a caregiver/sitter (temporary, scoped, auto-expiring view). Read
docs/phase2-tickets/00-README.md.
AUTONOMY: don't ask; mirror the existing consent model and pick sensible scopes/defaults, then proceed.
CI green → auto squash-merge; red → fix then merge. Keep going through Wave 5. One branch off origin/main.
Branch ticket/family-caregiver-sharing. Gates: npm test (web vitest + mobile jest); npm run
test:integration (RLS — this is access-control, prove it hard).

CONTEXT (reuse the proven primitive)
- care_access_grants + assertCareAccess + care_access_audit (migrations 0015/0023) gate PROVIDER access
  to a pet by scope, with an append-only audit + instant revoke. This ticket applies the SAME shape to a
  PERSON (another user_profiles) instead of a provider.
- Identity: user_profiles.id; pets.owner_user_id = the owner.

GOAL: an owner invites another user to a pet as either FAMILY (co-manage: see + edit the pet's profile,
health, routines, like a co-owner) or CAREGIVER (temporary: see feeding/med instructions + emergency
info, optionally log visits, with an expiry). The grantee accepts; access is scoped, audited, and
revocable instantly. Owner remains the only one who can delete the pet / remove others.

SCOPE
- Migration (next free ≥0046): pet_caregivers (or pet_people_grants) — (id, pet_id, owner_user_id,
  grantee_user_id, role ['family','caregiver'], scopes/derived from role, status
  ['pending','active','revoked'], expires_at nullable, created_at). + an append-only audit
  (reuse/parallel care_access_audit). ENABLE+FORCE RLS: the OWNER manages grants for their pets; the
  GRANTEE sees grants naming them; a SECURITY DEFINER helper app_user_has_pet_access(pet_id, scope) (mirror
  app_provider_has_grant) that the pet's data-table policies can consult. Then EXTEND the relevant pet
  data tables' RLS so an active family/caregiver grantee can read (and, for family, write) within scope —
  additively, without breaking owner-only access. This is the careful part: do it table-by-table for the
  scopes the role needs, with harness proofs (grantee sees only granted scope; expired/revoked → zero;
  caregiver can't do family-only actions; non-grantee sees nothing). Flag migration in test-backlog.
- Routes: owner invite (by @handle/username — reuse owner search), accept/decline (grantee), list
  (owner: who has access; grantee: pets shared with me), revoke (owner), with audit writes via the helper.
- Mobile: an owner "Share with family/caregiver" screen (invite + manage + revoke, with role + optional
  expiry); a grantee "Shared with me" view; caregivers see the scoped read (feeding/med/emergency) and,
  if allowed, log visits. Reuse existing pet UI; gate by the grant.
- Tests: integration — owner grants family → grantee reads+writes in scope; caregiver → read-only scoped +
  expiry enforced; revoke → instant zero; non-grantee zero; owner-only delete/remove. web/mobile flows.

DO NOT: weaken owner-only deletion or the no-cross-user-leak rule (this is a DELIBERATE, scoped, audited
crossing — keep it tight); grant more than the role's scope; skip the audit; add a provider path here
(this is person↔person). Migration hand-applied by Tats — flag it.

VERIFY: npm test + integration green. PR body: the person-grant model mirroring care_access, the per-table
RLS extensions with proofs, family vs caregiver scopes, expiry + instant revoke + audit. DEVICE: invite a
family member → they co-manage; invite a caregiver with expiry → scoped view; revoke → access gone.
```
