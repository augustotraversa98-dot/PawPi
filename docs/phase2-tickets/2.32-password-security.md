# 2.32 — Password security rules

Read `00-README.md` (incl. the **Wave 5 autonomy preamble**) first. Web (auth) + mobile (signup UI).
No migration. Independent. Security.

```
ORIENTATION
PawPi web auth + Expo mobile. Phase-2 ticket 2.32: enforce password strength. Read
docs/phase2-tickets/00-README.md.
AUTONOMY: build without asking; if any choice is ambiguous pick the most standard/sensible option and
proceed — never stop for input. CI green → squash-merge automatically; CI red → debug, fix, merge when
green. Keep working down the Wave 5 queue until tokens run out, then resume after reset. One fresh branch
off origin/main per ticket. NO migration.
Branch ticket/password-security. Gate: npm test (web vitest + mobile jest).

CONTEXT
- apps/web/src/auth.js — the Credentials provider (~line 262) where sign-up/sign-in is validated
  server-side. Today there is NO password strength check (a "123456" is accepted).
- apps/mobile/src/utils/auth/* + the web auth pages — the sign-up UI (mobile auth flows through the web
  AuthWebView, so the web sign-up form is the primary surface).

GOAL: new passwords must meet a clear strength bar, enforced SERVER-SIDE (the source of truth) and
mirrored with live client-side feedback. Existing users are NOT locked out (the rule applies on
sign-up and password-change only, never retroactively on login).

SCOPE
- Define one shared rule (recommended: min 8 chars AND at least 3 of {lowercase, uppercase, digit,
  symbol}, reject obvious common passwords like "password"/"123456" via a small blocklist). Keep it in a
  pure, testable helper.
- Enforce it server-side in the sign-up/credentials path (reject weak with a clear message). Do NOT touch
  the LOGIN check for existing accounts (they must still sign in with whatever they have).
- Client: live strength meter + inline requirements on the sign-up form (and the password-change form if
  one exists); disable submit until valid.
- Tests: the validator (accept strong, reject short/common/low-variety); the server path rejects a weak
  sign-up; login of an existing weak password is unaffected.

DO NOT: lock out or force-reset existing users; weaken or alter the login path; store anything new;
rewrite auth.js's Supabase adapter/core (only add the strength check in the sign-up path). No migration.

VERIFY: npm test green (baseline + net-new). PR body: the rule, server enforcement, client meter,
existing-users-unaffected. No device gate required (browser-checkable).
```
