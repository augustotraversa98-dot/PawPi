Read `00-README.md` + `../phase2-superapp-master-plan.md` (§2.6 dashboards) first. Depends on: 2.4

```
ORIENTATION
PawPi web provider dashboard. Phase-2 ticket 2.24: a CALENDAR view of bookings/appointments — the
provider's primary daily screen. Read docs/phase2-tickets/00-README.md + master plan §2.6.
Branch ticket/provider-calendar-view off origin/main; squash-merge. NO migration.
Gate: npm test (web vitest). Confirm the web baseline first.

CONTEXT (read before editing)
- apps/web/src/app/api/providers/[id]/bookings/route.js — the bookings inbox (booking-context joins ONLY:
  pet name, owner name, service name; NO medical tables). The calendar reads from this (extend it to
  return the fields the grid needs, still booking-context only).
- supabase/migrations/0030_generalized_booking.sql — bookings = vet_appointments + capability + start_at/
  end_at + booking_status + the provider_bookings VIEW + provider_location_id + staff_user_id. The slot
  times (start_at/end_at) drive the grid.
- 2.3 payments — an order's amount + paid/unpaid status (kind='booking', source_ref→booking) gives the
  value + paid flag per booking. 2.4 carries an optional deposit order link. Surface value/paid if present.
- apps/web/src/app/provider/ dashboard shell + @tanstack/react-table + recharts (already deps). Build the
  calendar with existing libs (a CSS grid is fine — no new heavy calendar dep unless trivial).

GOAL: a week/day calendar where DATES are columns across the top and TIMES are rows down the left, each
booking rendered in its slot showing: the pet + owner, what they booked (service/capability), notes, key
user/pet info, the value + paid/unpaid, and the location (in-store vs house visit). Scoped to the ACTIVE
provider only (never another business's bookings).

SCOPE
1. Extend GET /api/providers/[id]/bookings (or add a ?view=calendar / date-range param) to return, per
   booking: id, start_at/end_at, capability, service name, pet name + basic pet info, owner name,
   booking notes, location (provider_location_id → in-store, or a house-visit/address flag if the booking
   carries one), booking_status, and value_cents + paid (from the linked order/payment, when present).
   Booking-context joins ONLY — NO medical tables (assert in tests, same rule as the inbox). assertCareAccess
   is NOT used here; the active-staff scoping on the provider's own bookings is the gate.
2. Web calendar component: dates as columns, times as rows, bookings positioned by start_at/end_at;
   week + day views; navigate weeks; click a booking → a detail popover with the full info + the existing
   confirm/decline/cancel/assign actions (reuse the inbox PATCH actions, don't rebuild). Visual cues for
   paid/unpaid + location.
3. Make the calendar the dashboard's primary bookings surface (Dashboard home links into it; keep the
   list/inbox available as an alternate view).
4. Empty states (no bookings that week → a clean empty grid, no fake events). Scoped to the active
   provider; switching providers recomputes.
5. Tests: vitest — the calendar data route returns the grid fields + value/paid + location, only
   booking-context (no medical tables touched, asserted); cross-provider isolation (another provider's
   bookings never returned); the component places bookings in the right day/time cells + the detail
   actions call the existing PATCH.

DO NOT: add a migration; read medical tables in the calendar path; show another provider's bookings; add a
heavy 3rd-party calendar dep if a simple grid does it; rebuild the booking-action endpoints (reuse 2.6b's
PATCH).

VERIFY: npm test (web) green (baseline + net-new). PR body: the calendar data fields (incl. value/paid/
location), the columns=dates / rows=times grid + week/day, reuse of the inbox actions, cross-provider
isolation, no migration. No device check (web; verify in browser). Note this is provider-facing UI on the
deferred provider-device-pass posture.
```
