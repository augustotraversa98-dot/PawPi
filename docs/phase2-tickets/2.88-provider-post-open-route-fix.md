# 2.88 — Fix: tapping a business post as a pet owner opens a dead "screen doesn't exist" page

**Status:** ready · no migration · independent · safe-parallel: yes (mobile posts list + the post-detail
route only) · **do FIRST**

## Context
The provider-post comments feature (2026-08-10 session, PR #338) shipped a mobile post-detail screen at
`anything/apps/mobile/src/app/service/provider-post.jsx` (Expo Router; sibling routes in that folder:
`provider.jsx`, `place.jsx`, `shop.jsx`). Provider post cards were made tappable in the posts panel so a
pet owner can open a post and read/write comments.

## Current issue
Tapping a provider post card (as a pet owner) navigates to `/service` — which is not a real route — so
Expo Router shows its "Uh-oh! This screen doesn't exist (yet)." fallback (confirmed on device). The
`provider-post.jsx` detail screen is never reached, so a pet owner currently **cannot open a post at all**,
which also makes the new comments feature unreachable/untestable.

## Expected behavior
1. Tapping a provider post card opens the post-detail screen (`service/provider-post`) with the correct
   params (provider id + post id), showing the post body, its images, and its comments.
2. Use the **same router navigation pattern the other `service/*` screens already use** (e.g.
   `router.push({ pathname: '/service/provider-post', params: { … } })`) — do not invent a new route name
   and do not hand-build a `/service` path that resolves to the folder root.
3. Fix the same navigation from any other surface that renders provider post cards (check `place.jsx` and
   the provider profile/posts panel) so every entry point opens the detail screen, not the fallback.
4. Guests (unauthenticated) can still open and READ the post + comments; the composer stays gated to
   signed-in users (unchanged from PR #338).

## Data / API rules
No migration, no API change — this is a mobile client navigation fix only.

## Acceptance criteria
- Root-cause first: identify exactly what the card's tap handler / `href` emits today and why it resolves
  to `/service`; state it in the PR body.
- A mobile jest test asserts the post card navigates to the real `provider-post` route with the right
  params (this is the regression guard against the `/service` fallback).
- `npm test` (mobile jest) green, baseline + net-new, nothing pre-existing broken.
- DEVICE PASS (iOS Simulator, seeded demo account per `docs/dev-pipeline.md`): tap a business post → the
  detail screen opens with body + images + comments; add a comment as a signed-in pet owner and it
  persists; a guest can open and read but sees the sign-in prompt instead of the composer.
- Update `docs/roadmap.md` + `PawPi_instructions.md` status block + one line in `docs/night-run-log.md` on
  merge.
