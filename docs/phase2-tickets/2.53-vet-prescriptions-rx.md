# 2.53 — Prescriptions / Rx (a section INSIDE Veterinary, not a separate pharmacy)

Read `00-README.md` (Wave 6 order + the ⚡ autonomy preamble) first. Web + mobile + migration. **Product
decision (Tats):** Rx is NOT a standalone `pharmacy` storefront capability — it's a **prescriptions
section inside the existing Veterinary flow + the Vet Record**. A vet issues a prescription to a pet; the
owner sees it in their Vet Record and can request a refill. Medical = STRICTEST RLS — model it on the
clinical-write path (vet_notes / provider records), where the vet writes and the owner reads.

```
ORIENTATION
Read ARCHITECTURE.md and supabase/SCHEMA_NOTES.md to get oriented, then this task. PawPi Expo mobile +
web API. Phase-2 ticket 2.53: prescriptions / Rx as a section INSIDE the Veterinary service + the Vet
Record (NOT a new pharmacy capability/storefront). Read docs/phase2-tickets/00-README.md (shared
conventions; medical tables = strictest RLS; the Wave 5 autonomy preamble applies).
AUTONOMY: don't ask; pick the sensible, on-brand, clinically-safe option and proceed. CI green → auto
squash-merge; red → fix then merge. One fresh branch off origin/main: ticket/vet-prescriptions-rx.
Gates: npm test (web vitest + mobile jest); npm run test:integration (real-Postgres RLS).

CONTEXT
- The clinical-write pattern already exists: a provider with the vet capability + a consent grant
  (care_access_grants / assertCareAccess) or a booking can write to a pet's medical record; the OWNER
  reads. vet_notes is append-only and RLS-proven in provider-records-rls.integration.test.ts (provider
  INSERT ok; provider UPDATE/DELETE → 0 rows; owner reads/manages own). MIRROR that integrity model.
- The Vet Record (mobile) already aggregates Current Medications from Medical Care routines/logs. Rx is
  related but distinct: a Current Medication is what the owner is giving; a PRESCRIPTION is what a vet
  authorized (drug, dose, route, duration, refills-remaining). Keep them DISTINCT but show prescriptions
  in the Vet Record alongside medications, clearly labeled "Prescribed by {clinic}".
- Telehealth (2.18) and in-person vet bookings already exist — a prescription can originate from either.
- Health positioning: the app does NOT diagnose or prescribe; it RECORDS a prescription a licensed vet
  issued. Owners cannot self-issue a prescription. Keep the non-diagnostic framing.
- Fulfillment (delivery/pickup, charging for the med) is OUT OF SCOPE v1 — if wanted later it reuses
  shop/e-commerce (2.11) + payments (2.3). Note as a follow-up; v1 is issue → view → request refill →
  vet approves/declines.

GOAL
A vet (provider staff with the vet capability + access to the pet) issues a prescription to a pet from the
provider dashboard; the owner sees it in their Vet Record under a Prescriptions section with the full
detail (drug, strength, dose, route, frequency, duration, quantity, refills remaining, instructions,
issuing vet/clinic, date); the owner can REQUEST A REFILL; the vet approves (decrements refills) or
declines. Append-only clinical integrity: the owner can never edit/forge a prescription; the issuing
provider can issue + manage refill decisions but cannot silently rewrite history.

SCOPE
- Migration (next free ≥0053 — check supabase/migrations/ at build time; expected 0053):
  prescriptions (id, pet_id, owner_user_id, provider_id, issued_by_staff_id [FK provider_staff],
  source text ['in_person','telehealth'] nullable, drug_name text, strength text nullable, dose text,
  route text nullable, frequency text, duration text nullable, quantity text nullable,
  refills_authorized int default 0, refills_remaining int default 0, instructions text, status text
  ['active','completed','cancelled'] default 'active', issued_at timestamptz default now(), created_at).
  rx_refill_requests (id, prescription_id, pet_id, owner_user_id, status text
  ['requested','approved','declined'] default 'requested', requested_at, decided_at nullable,
  decided_by_staff_id nullable, note text). ENABLE+FORCE RLS, STRICTEST (medical):
    • prescriptions: the OWNER READS own (no insert/update/delete by owner). A provider STAFF member with
      the vet capability AND access to the pet (consent grant or booking) INSERTs and may UPDATE only the
      refill/status transition fields for THEIR provider's rows — model the append-only integrity like
      vet_notes (no owner write; provider can't edit another provider's Rx; no hard delete — cancel via
      status). Use assertCareAccess / app_provider_has_grant / app_provider_has_booking +
      app_is_active_staff_of; add a SECURITY DEFINER helper if a predicate must read another RLS table
      (pinned search_path, GRANT EXECUTE to pawpi_app; mind recursion).
    • rx_refill_requests: the OWNER INSERTs a request on their own active prescription + reads own; the
      issuing provider's staff reads requests for their prescriptions + UPDATEs the decision
      (approved/declined) which decrements refills_remaining on approve (do the decrement server-side /
      via a DEFINER helper so the owner never writes prescription fields).
  Harness proofs: vet with access issues an Rx; owner reads but cannot insert/edit/delete it; another
  provider's staff sees nothing; owner files a refill request on own Rx; the issuing vet approves →
  refills decrement; owner cannot approve own refill or edit the Rx; non-grantee provider can't issue.
  Flag in docs/test-backlog.md ACTION 1 (Tats hand-applies).
- Web (provider dashboard, reuse the shell + the existing pet/clinical view): in the vet's view of a pet
  (the same place vet_notes/records are written), an "Issue prescription" form + a list of that pet's Rx
  this provider issued + a refill-requests queue with approve/decline. Capability + access gated.
- Mobile (owner-facing, Vet Record): a Prescriptions section — list (newest first) with detail (all
  fields + issuing clinic), a "Request refill" action on active Rx with refills remaining, and refill-
  request status. Empty state when none ("No prescriptions yet"). Clearly labeled "Prescribed by {clinic}"
  and distinct from owner-entered Current Medications. NO owner create/edit of the prescription itself.
- Tests: web vitest (vet with access issues Rx; owner-read-only; refill request → vet decision decrements;
  capability/access gating; cross-provider isolation; owner can't forge/edit); integration (prescriptions
  + rx_refill_requests RLS append-only integrity proven as pawpi_app: provider INSERT ok / provider
  cross-edit denied / owner read-only / refill decrement via the safe path / outsider zero; completeness
  guard green); mobile jest (Rx list + detail render from real data; request-refill posts the right body;
  empty state; no owner edit affordance on the Rx).

DO NOT: make this a separate pharmacy capability/storefront (it lives inside Veterinary + the Vet Record);
let the OWNER create/edit/delete a prescription (owner reads + requests refills only); let a provider edit
another provider's Rx or hard-delete history (cancel via status); let the owner write prescription fields
when requesting/decrementing a refill (server/DEFINER only); diagnose or auto-suggest a drug; build
medication fulfillment/charging (follow-up via shop+payments); show fake prescriptions. Migrations hand-
applied by Tats — flag in test-backlog ACTION 1.

VERIFY: npm test + integration green; completeness guard green. PR body: prescriptions + rx_refill_requests
with STRICTEST append-only RLS proofs (vet-with-access writes, owner read-only, refill decision decrements
safely, cross-provider isolation), the dashboard issue/approve flow, the Vet Record Prescriptions section.
DEVICE/BROWSER: as a vet with access, issue an Rx to a pet → it appears in that owner's Vet Record labeled
by clinic; owner requests a refill → the vet sees + approves → refills remaining drops; owner cannot edit
or forge an Rx; a different clinic never sees it; empty Vet Record shows the empty state.
```
