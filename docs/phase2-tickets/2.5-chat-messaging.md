# 2.5 — Chat / messaging (owner ↔ provider)

Read `00-README.md` + `../phase2-superapp-master-plan.md` §2 first.

```
ORIENTATION
PawPi web API + mobile. Phase-2 ticket 2.5: owner ↔ provider messaging, needed by walkers/sitters/
adoption/etc. Read docs/phase2-tickets/00-README.md + master plan §2, the provider spine + 2.1
capabilities + 2.4 bookings (a thread is usually scoped to a provider relationship / a booking), and a
recent RLS migration for the pattern.
Branch ticket/chat-messaging off origin/main; squash-merge; migration hand-applied after merge.
Gates: npm test + npm run test:integration (participant-scoped RLS is the crux).

GOAL: real-time-ish 1:1 threads between an owner and a provider (its staff), optionally tied to a
booking; unread counts; reuse Supabase Storage for image attachments.

SCOPE
- Migration (RLS'd): message_threads (id, owner_user_id, provider_id, booking_id?, created_at,
  last_message_at) + messages (id, thread_id, sender_user_id, body, attachment_url?, created_at,
  read_at?). 
  RLS — PARTICIPANT-SCOPED: a thread/messages are visible+writable to (a) the owner (owner_user_id =
  current_app_user_id()) and (b) active staff of provider_id (app_is_active_staff_of). No one else.
  Sender must be a participant. Harness proofs (owner sees own threads; provider staff see their
  provider's threads; outsider → zero; non-participant cannot post) + completeness guard.
- Routes: list my threads (owner side + provider side), get/post messages, mark read, start a thread
  (from a provider profile or a booking). Pagination. Unread count.
- Realtime: use Supabase Realtime if straightforward, else polling on a short interval (document the
  choice; don't over-build).
- mobile: a Messages screen (threads list + conversation) on the owner side; provider side gets a
  thread list in the web dashboard (a "Chats" section — was a coming-soon stub). Reuse Storage upload
  for image attachments.
- Vitest + integration: thread/message CRUD; participant RLS (the key proofs); unread.

DO NOT: expose threads to non-participants; allow posting as another user; build heavy realtime infra
if polling suffices. No fake messages.

VERIFY: npm test + integration green (baseline + net-new) incl. participant RLS. PR body: the model,
participant scoping, realtime choice. Migration hand-applied after merge. Confirm origin/main.
```
