# 2.68 — Shared Apple-Maps location component (Wave 7 foundation)

Read `00-README.md` (the ⚡ autonomy preamble + shared conventions) first. Mobile-only, NO migration.
**Build FIRST in Wave 7** — it is the cross-cutting map requirement every later location section reuses.

Decided with Tats (2026-06-18): **every section that captures OR shows an address/location must use a real
map** (Apple Maps on iOS for now). The app already renders maps with `react-native-maps` +
`PROVIDER_DEFAULT` (= Apple Maps on iOS, polyfilled to Google on web) — `WalkMapPicker` (2.43) is the proven
pattern. Do NOT introduce a new map library; do NOT rebuild per-screen pickers. Extract ONE shared set of
components and reuse them everywhere, exactly per the "reuse don't rebuild" rule.

```

and adopt it across the app. Read docs/phase2-tickets/00-README.md (shared conventions; the autonomy
preamble applies). No DB work, no provider_type gating — pure mobile UI refactor + new shared components.

Gates: npm test (mobile jest is the relevant suite here; keep web vitest green/unchanged).

CONTEXT
- The map stack ALREADY EXISTS: anything/apps/mobile/src/components/SocialWalks/WalkMapPicker.jsx uses
  `import MapView, { Marker, PROVIDER_DEFAULT } from "react-native-maps"`; the web polyfill is
  anything/apps/mobile/polyfills/web/maps.web.jsx (@teovilla/react-native-web-maps, Google on web). On iOS,
  PROVIDER_DEFAULT renders Apple Maps with NO API key required. Keep using PROVIDER_DEFAULT (Apple on iOS).
- `expo-location` is already a dep (WalkMapPicker calls requestForegroundPermissionsAsync /
  getCurrentPositionAsync). isValidCoord lives in @/utils/walkBuddies.
- Today only social walks (2.43) and transport (2.52) capture a location; lost & found (2.48) drops a pin.
  Going forward EVERY location/address field must be a map, so we need shared, reusable pieces.

GOAL
Three reusable, well-tested components in anything/apps/mobile/src/components/Map/ that any screen can drop
in, plus a refactor of the existing pickers to use them (no behavior change), so "Apple Maps in every
location section" is satisfied by reuse, not copy-paste.

SCOPE
- New shared components (anything/apps/mobile/src/components/Map/):
  • MapLocationPicker.jsx — generalize WalkMapPicker: props { value:{lat,lng}|null, onChange({lat,lng}),
    height?, showAddress?, label?, testID }. Tap-to-drop + draggable marker + "My location" (expo-location,
    graceful if denied) + a "Pinned · lat,lng" / address readout. PROVIDER_DEFAULT.
  • MapLocationView.jsx — read-only display: props { points:[{lat,lng,...}]|{lat,lng}, markers?, polyline?,
    height?, interactive?:false }. Renders one or more markers and an optional Polyline (for routes). Used
    by detail screens that SHOW a saved location/route on a real map.
  • LocationField.jsx — a form-row wrapper: a labeled, tappable summary ("Set location on map") that opens
    MapLocationPicker in a bottom sheet/modal and writes back {lat,lng,address?}. This is the standard
    drop-in any form uses for an address/location field.
- Address text: keep an editable address text input alongside the pin (manual entry stays possible). A
  pin-to-address lookup (reverse geocode) is OPTIONAL — use expo-location's reverseGeocodeAsync if trivial,
  else leave the address as a manual field; do NOT add a new geocoding dep/key in this ticket. No fake data.
- Refactor (no behavior change, keep tests green): point WalkMapPicker (2.43 create-walk) and the transport
  booking picker (2.52) at MapLocationPicker (WalkMapPicker can become a thin wrapper or be replaced at its
  call sites). The lost & found pin (2.48) may also adopt MapLocationPicker if low-risk; otherwise leave it
  and note as follow-up.
- Web: ensure the components work through the existing maps.web.jsx polyfill (Google on web) — no new web
  map work; just don't break web by importing iOS-only APIs unconditionally.
- i18n: any new user-facing strings go through t() with EN+ES (2.29 pattern): "Set location on map",
  "My location", "Tap the map to drop a pin", "Pinned".
- Tests: mobile jest — MapLocationPicker fires onChange on map press + drag + "My location"; renders an
  existing pin; LocationField opens the picker and writes the value back; MapLocationView renders markers +
  a polyline from real points and an empty state for none. Mock react-native-maps as the existing tests do.

DO NOT: add a new map SDK or a maps API key (PROVIDER_DEFAULT = Apple on iOS needs none); change the web
polyfill; remove manual address entry; introduce fake/placeholder coordinates; regress WalkMapPicker /
transport picker behavior or their tests. NO migration.

VERIFY: npm test green (mobile jest baseline + net-new; web vitest unchanged). PR body: the three shared
Map components (Apple Maps via PROVIDER_DEFAULT), the call-site refactor, and that every future
location/address section now has a single drop-in. DEVICE: open create-walk + book-transport → the map is
Apple Maps on iOS, pin drop / drag / "My location" all work; a saved location shows on a real map in detail
views. (This component is the dependency for 2.70 live map, 2.73 places, 2.74 events.)
```
