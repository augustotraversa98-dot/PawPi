# 2.80 — Calendar everywhere: bookings, transport, telehealth & events (Wave 8)

Read `00-README.md` (the ⚡ autonomy preamble + shared conventions) first. Mobile + web API + migration. ⛔
**Build AFTER 2.79** (reuses its unified calendar layer + ICS route). Extends the now-unified calendar
integration to every remaining scheduled surface: generalized service bookings (grooming / walking / daycare
/ sitting), transport trips, telehealth consults, and community events/meetups — each with add /
update-on-edit / remove-on-cancel, persisting the device event id for the round-trip.

```
ORIENTATION
Read ARCHITECTURE.md and supabase/SCHEMA_NOTES.md to get oriented, then this task. PawPi Expo mobile + web
API. Wave-8 ticket 2.80: wire add-to-calendar into all remaining scheduled surfaces. Read
docs/phase2-tickets/00-README.md (shared conventions; the ⚡ autonomy preamble applies). PREREQ: 2.79
(unified calendar layer + ICS route) merged to origin/main — verify before building.
AUTONOMY: don't ask; pick the sensible, on-brand option and proceed. CI green → auto squash-merge; red → fix
then merge. One fresh branch off origin/main: ticket/calendar-everywhere.
Gates: npm test (web vitest + mobile jest); npm run test:integration (real-Postgres RLS). Migration: take the
NEXT FREE number in supabase/migrations/ at build time (expected 0063); leave it in the folder, flag in
docs/test-backlog.md ACTION 1 — Tats hand-applies. Do NOT auto-apply to Supabase.

CONTEXT
- 2.79 (merged) provides getOrCreatePawPiCalendar({ title, color, name }) + upsertCalendarEvent /
  deleteCalendarEvent + the pure src/utils/calendarFormat.js module + GET /api/calendar/booking/[id].ics.
  REUSE them — do not re-implement the calendar layer.
- The booking spine is vet_appointments: grooming / walking / daycare / sitting / transport / telehealth are
  ALL vet_appointments rows and already carry a calendar_event_id column (0005). So those surfaces need NO
  new column — store the returned device event id into vet_appointments.calendar_event_id through the
  existing owner booking routes, and update/delete it on edit/cancel, exactly like VetAppointmentRoutineModal
  already does for vet appointments. Transport detail is transport_trips (0052), keyed to its booking by
  booking_id → use transport_trips.scheduled_at + pickup/dropoff address for the event time/location/notes.
  Telehealth is telehealth_sessions (0040) on a vet_appointments booking — a video consult, no physical
  location.
- Community events (0060): events has starts_at / ends_at / location; RSVPs are per-user in event_rsvps. A
  device calendar event is PER ATTENDEE, so the calendar_event_id must live on the user's event_rsvps row,
  NOT the shared events row. That is the ONLY new column this ticket needs.

GOAL
From any scheduled item — a confirmed service booking, a transport trip, a telehealth consult, or an RSVP'd
event — the owner can add it to their device calendar (Apple on iOS), and editing/cancelling updates/removes
that calendar event. Plus ICS export for events. No fake data; calendar is always OPTIONAL and never blocks
the underlying save (degrade clean if permission is denied), following the existing vet-appointment
precedent.

SCOPE
- Mobile: add an "Add to calendar" affordance (reusing 2.79's layer, with a per-surface calendar title/color
  via getOrCreatePawPiCalendar) on: (a) the generalized booking detail/confirmation for grooming / walking /
  daycare / sitting; (b) the transport trip screen (scheduled_at + pickup/dropoff address as location/notes);
  (c) the telehealth session (the consult time; note it's a video consult, no physical location); (d) the
  events screen, for an event the user has RSVP'd "going". Persist the returned eventId — bookings /
  transport / telehealth → vet_appointments.calendar_event_id via the existing owner route; events →
  event_rsvps.calendar_event_id. On reschedule (edit) → update the calendar event; on cancel / un-RSVP →
  delete it. Permission denied / unavailable degrades cleanly (toast; NEVER blocks the underlying save) —
  mirror addVetAppointmentToCalendar's existing return-shape handling.
- Migration (next free, expected 0063): ALTER TABLE event_rsvps ADD COLUMN IF NOT EXISTS calendar_event_id
  text. Additive column on an existing RLS'd, own-row-scoped table — NO policy change; the column rides the
  existing event_rsvps own-row policies. Idempotent. Re-run the harness proof that a user reads/writes only
  their OWN event_rsvps (including the new column) and another user gets nothing; completeness guard stays
  green. Flag in docs/test-backlog.md ACTION 1.
- Web: extend 2.79's ICS export with GET /api/calendar/event/[id].ics — owner/visibility-scoped to events the
  caller can see (published, non-deleted — same visibility as the events listing). Build the VEVENT from
  starts_at/ends_at/location with the same RFC 5545 escaping as the booking route.
- Backend (web owner routes): ensure the booking / transport / telehealth owner PATCH/cancel routes accept +
  persist + clear calendar_event_id (the column already exists on vet_appointments), and the event RSVP route
  persists/clears event_rsvps.calendar_event_id. Keep all of these owner-scoped.
- i18n: new strings via t() EN+ES.
- Tests: web vitest — the booking / event routes persist + clear calendar_event_id; the events ICS route
  builds a valid VEVENT from a mocked event and is auth + visibility gated. integration — event_rsvps RLS is
  still own-row-only INCLUDING the new column (proven as pawpi_app; another user can't read or set it);
  completeness guard green. mobile jest — each surface's add/update/delete calls the 2.79 layer with the
  correct details; permission-denied degrades without blocking the save; the events "add to calendar" is
  gated on a "going" RSVP.

DO NOT: rebuild the calendar layer (reuse 2.79); add calendar_event_id to vet_appointments (already there) or
to the shared events row (it's per-attendee → event_rsvps); block the save when calendar permission is
denied; change event_rsvps / booking RLS policies (the new column rides existing own-row/owner policies);
ship fake/sample events; use a non-Apple map/calendar on iOS. Migration hand-applied by Tats — flag in
docs/test-backlog.md ACTION 1.

VERIFY: npm test + integration green; completeness guard green. PR body: the per-surface add/update/delete
wiring (bookings / transport / telehealth → vet_appointments.calendar_event_id; events → new
event_rsvps.calendar_event_id), migration 0063 + its RLS proof, the events ICS route, and the degrade-clean
permission handling. DEVICE: add a grooming booking, a transport trip, a telehealth consult, and an RSVP'd
event to the calendar; reschedule one → the calendar event moves; cancel / un-RSVP → it's removed; deny
calendar permission → the booking/RSVP still saves with a clean message.
```
