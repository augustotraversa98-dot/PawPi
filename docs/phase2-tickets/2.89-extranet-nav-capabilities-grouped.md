# 2.89 — Extranet left-nav shows only the offerings selected on the Business Profile, grouped & simplified

**Status:** ready · no migration · independent · safe-parallel: yes (provider dashboard nav + the profile
offering picker) · presentation-only (NO capability-key changes)

## Context
Providers hold MANY capabilities via `provider_capabilities` (ticket 2.1); onboarding/profile is a
multi-select and every service module gates on a capability (never on a single `provider_type`). The
provider web dashboard lives in `anything/apps/web/src/app/provider/` (React Router v7 shell,
`ProviderShell` nav, `capabilities.js`). The left-hand nav currently lists offering entries that don't
faithfully track what the business actually selected on its profile, and the flat list of ~11 offerings is
hard to scan.

## Current issue
1. The left-nav categories don't match the offerings the business selected on its Business Profile — an
   offering that isn't selected can still show, and selecting/deselecting on the profile doesn't cleanly
   drive what appears in the nav.
2. The offerings are presented as one long flat list, which is confusing to a business owner.

## Expected behavior
1. **Capability-driven nav.** The left-nav offering entries reflect EXACTLY the capabilities the provider
   has selected on its Business Profile: selected → visible; not selected → hidden, appearing only once the
   business enables it on the profile. Wire the nav to the same capabilities source the profile editor
   writes, reactively (enable on profile → the nav entry appears; disable → it disappears). Always-present
   structural items (Business Profile, Storefront/Posts, etc.) stay regardless.
2. **Grouped, simplified taxonomy — presentation only, NO key changes, NO migration.** Group the offerings
   under a few clear parent sections in BOTH the profile offering-picker and the left nav. Keep every
   underlying capability key exactly as-is — this is labels + grouping only, fully reversible.
   **Recommended grouping (implement this):**
   - **Veterinary & Health** — Vet clinic (`vet`), Telehealth (`telehealth`), Grooming (`groomer`),
     Pharmacy / Rx (only if a distinct key already exists — else omit this leaf)
   - **Walking & Sitting** — Dog walking (`walker`), Pet sitting (`sitter`), Daycare / Boarding (`daycare`)
   - **Training** — Training (`trainer`)
   - **Store** — Products (`shop`)
   - **Adoption** — Adoption (`adoption`)
   - **Other** — Transport (`transport`), Insurance (`insurance`)
   Map each EXISTING capability key into a section as above. **Do NOT create, rename, or remove any
   capability key.** If a key exists that isn't listed here, place it in the most sensible section.
3. Selection stays clear, fast, and obvious — plain labels, short helper text where useful, no internal
   jargon (see 2.90 for the copy rule).

## Data / API rules
No migration, no schema change, no capability-key change. Reads the existing `provider_capabilities` the
profile already writes. If any read touches RLS, prove it in the integration harness; otherwise reuse the
existing proven reads.

## Acceptance criteria
- `npm test` (web vitest) green + baseline; `npm run test:integration` only if a policy changed (else none).
- Web tests: the nav renders ONLY the selected offerings; toggling an offering on the profile adds/removes
  its nav entry; the grouped sections render with the right leaves under each.
- No capability key added/renamed/removed (grep the diff to confirm this is labels + grouping only).
- DEVICE / dashboard pass: enable an offering on the profile → it appears in the left nav; disable it → it
  disappears; the grouped sections read cleanly for a single-offering business and a multi-offering one.
- Update `docs/roadmap.md` + `PawPi_instructions.md` status block + `docs/night-run-log.md` on merge; add
  the Wave 10 index entry to `docs/phase2-tickets/00-README.md`.
