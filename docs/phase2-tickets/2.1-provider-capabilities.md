# 2.1 — Provider capabilities (a provider offers MANY services) — FOUNDATIONAL

Read `00-README.md` (esp. the CORE MODEL section) + `../phase2-superapp-master-plan.md` §1.5 first.
Every later service module depends on this.

```
ORIENTATION
PawPi web API (anything/apps/web, React Router + vitest + real-PG harness). Phase-2 ticket 2.1: make a
provider able to offer MULTIPLE capabilities (a "vet shop" = consultation + vaccination + grooming +
store), replacing the single providers.provider_type as the feature switch. Read
docs/phase2-tickets/00-README.md + docs/phase2-superapp-master-plan.md §1.5. Also read 0014_providers.sql
(providers + provider_type), the onboarding/profile routes (api/providers/route.js POST/GET,
[id]/route.js PATCH), discovery (discover/route.js, public/[slug]/route.js), and a recent RLS migration
(0024/0025) + the providerAuth helpers for the pattern.
Branch ticket/provider-capabilities off origin/main; squash-merge; migration hand-applied after merge.
Gates: npm test green + net-new; npm run test:integration green + RLS proofs for the new table.

GOAL: one provider → many capabilities, each unlocking its module; discovery + onboarding + a gating
helper all keyed on capability, not provider_type.

SCOPE
- Migration (next number): new table provider_capabilities (id, provider_id FK→providers, capability
  text, created_at; UNIQUE(provider_id, capability)). Capability allowed set: vet, groomer, walker,
  daycare, sitter, trainer, shop, adoption, transport, pharmacy (CHECK or app-validated — your call,
  document). BACKFILL: insert one row per existing provider from its current provider_type. Keep
  provider_type column as an optional primary/display category (do NOT drop it; stop using it to gate).
  ENABLE+FORCE RLS on provider_capabilities: SELECT = published provider's caps are public (any authed,
  for discovery) OR active staff; write = app_is_provider_admin(provider_id). Mirror the providers
  policy shape. + harness proofs (owner/admin writes; public reads published caps; non-staff write
  denied).
- DB helper: a SECURITY-DEFINER providerHasCapability(provider_id, capability) (or SQL EXISTS in
  routes) for module gating; grant EXECUTE to pawpi_app.
- API:
  - Onboarding/profile: accept a capabilities[] array (multi-select) on provider create + a
    PATCH/endpoint to add/remove capabilities (owner|admin). Validate against the allowed set.
  - GET /api/providers/[id] + /public/[slug]: include the provider's capabilities[] in the response.
  - Discovery GET /api/providers/discover?type=<cap>: match providers that HAVE that capability (JOIN
    provider_capabilities), not provider_type. ?type omitted = all published. Public fields only.
  - A small requireProviderCapability(providerId, cap) guard helper for later module routes to call
    (so e.g. the grooming routes 403 if the provider lacks the groomer capability).
- Vitest for all routes (capabilities CRUD, discovery-by-capability, validation, isolation).

DO NOT: drop provider_type; gate any existing feature on provider_type after this (switch to
capability); change consent/medical access (capability ≠ data access); touch mobile UI here (the
mobile onboarding multi-select can be its own small follow-up, or note it). No fake data.

VERIFY: npm test baseline+net-new green; integration green incl. provider_capabilities RLS proofs +
completeness guard still passes. PR body: the many-capability model, backfill, discovery-by-capability,
providerHasCapability helper, and that provider_type is now display-only. Migration hand-applied after
merge. Confirm origin/main before the next ticket.

FOLLOW-UP (note, optional small ticket): mobile provider onboarding UI → multi-select capabilities;
and owner discovery filter chips by capability.
```
