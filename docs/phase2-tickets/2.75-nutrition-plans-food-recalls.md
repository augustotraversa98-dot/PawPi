# 2.75 — Nutrition plans + food-recall alerts (Wave 7)

Read `00-README.md` (the ⚡ autonomy preamble + shared conventions) first. Mobile + web API + migration.
Two linked owner-facing health features: a per-pet **nutrition plan** (ties to feeding routines) and
**food-recall alerts** (an external recall feed matched to the pet's food → notification). Honor the health
positioning: PawPi helps owners track + prepare vet conversations; it does NOT diagnose or prescribe a diet.

```
ORIENTATION
Read ARCHITECTURE.md and supabase/SCHEMA_NOTES.md to get oriented, then this task. PawPi Expo mobile + web
API. Wave-7 ticket 2.75: nutrition plans + food-recall alerts. Read docs/phase2-tickets/00-README.md
(shared conventions; the autonomy preamble applies) AND the Health positioning section of
PawPi_instructions.md (non-diagnostic copy).
AUTONOMY: don't ask; pick the sensible, on-brand option and proceed. CI green → auto squash-merge; red →
fix then merge. One fresh branch off origin/main: ticket/nutrition-food-recalls.
Gates: npm test (web vitest + mobile jest); npm run test:integration (real-Postgres RLS).

CONTEXT
- Owner+pet-scoped, like the other health data. Feeding routines already exist (Reminders & Routines →
  Feeding: meals with name/time/frequency); a nutrition plan complements them (food brand/product, portion,
  calories target, notes) — link to feeding where natural but do NOT rebuild feeding routines.
- Food-recall data is EXTERNAL (e.g. FDA/AAFCO pet-food recall feeds). Model it like the other external-key
  features (2.17 cron, 2.21 enrichment, 2.73 places): a server-side ingest behind an env key / scheduled
  job that, when unconfigured, DEGRADES CLEANLY (no recalls shown, no crash). PawPi has no built-in
  scheduler (per 2.17) — expose an idempotent ingest route hit by an external scheduler with a secret
  header (reuse the CRON_SECRET pattern), and FLAG the new env/cron need in test-backlog go-live actions.
- Health positioning (non-negotiable): nutrition copy must NOT diagnose or claim to prescribe a medical
  diet. Use the standard disclaimer pattern ("helps you track + prepare vet conversations; does not replace
  veterinary care"). Recall alerts are informational ("a product matching your pet's food was recalled —
  check with your vet").

GOAL
(1) An owner records a nutrition plan for a pet (current food brand/product, daily portion, target calories,
feeding notes, optional vet-shared) and sees it in Health; it complements feeding routines. (2) PawPi
ingests pet-food recalls from an external feed (server-side, key/cron-gated) and, when a recall matches a
pet's recorded food, raises a clear, non-diagnostic alert/notification. Real data + empty states; no fake
recalls, no fake plans.

SCOPE
- Migration (next free — check supabase/migrations/ at build time; expected 0061):
  nutrition_plans (id, pet_id FK pets, owner_user_id FK user_profiles, food_brand text, food_product text,
  food_form text nullable ['dry','wet','raw','mixed'], daily_portion text nullable, target_calories int
  nullable, notes text, active bool default true, created_at, updated_at, deleted_at). ENABLE+FORCE RLS,
  OWNER-SCOPED FOR ALL (owner reads/writes own; others zero) + the existing family/caregiver health-access
  pattern (0049) IF a plan should be visible to family — match how other health_* tables expose to family
  (reuse app_user_has_pet_access / app_user_has_pet_family); if simpler to keep owner-only for v1, do that
  and note family-visibility as a follow-up. Pick the on-brand option consistent with neighboring health
  tables.
  food_recalls (id, source text, external_ref text, brand text, product text, reason text, recall_date
  date, url text, raw jsonb, created_at, UNIQUE(source, external_ref)). Reference data (public, non-PII) —
  classify either any-authed READ with writes ONLY via a SECURITY DEFINER ingest path, OR RLS_EXEMPT with a
  one-line completeness-guard justification (it holds only public recall notices). Pick the simplest correct
  option and document it. Ingest is idempotent (the UNIQUE prevents dupes).
  Optionally a thin pet_food_recall_matches (pet_id, recall_id, owner_user_id, notified_at,
  dismissed_at, UNIQUE(pet_id, recall_id)) owner-scoped, so an alert can be shown/dismissed per pet without
  re-deriving — owner-scoped RLS like nutrition_plans. Add it only if it keeps the match/notify logic clean.
  Harness proofs as pawpi_app: owner manages own nutrition_plans (+ family access if added); food_recalls
  behaves per its classification; matches (if added) owner-scoped. Completeness guard green. Flag in
  test-backlog ACTION 1.
- Web API: nutrition_plans CRUD owner-scoped (reuse the owner-route pattern, e.g. like vet-record routes).
  A recall INGEST route (POST, x-cron-secret header like 2.17; idempotent upsert into food_recalls from the
  external feed; degrade-clean / "not configured" when the key is unset) + a matcher that, on ingest (or on
  a pet's plan change), finds nutrition_plans whose brand/product match a recall and raises a best-effort
  notification via app_notify (widen the notifications type CHECK additively for 'food_recall' if needed,
  drop+re-add like 0050/0051). An owner GET for "active recall matches for my pets."
- Mobile: in Health, a Nutrition card per pet — view/add/edit the plan (brand/product/portion/calories/
  notes) with the non-diagnostic disclaimer; show active feeding routines as context (read-only link, don't
  duplicate). A recall alert surfaces in Health/notifications when a match exists ("A product matching
  {pet}'s food was recalled — {reason}. Check with your vet." + link), dismissible. Empty states ("No
  nutrition plan yet", "No recalls affecting your pets"). No fake data.
- i18n: new strings via t() EN+ES, including disclaimers + the recall alert copy.
- Tests: web vitest (nutrition CRUD owner-scoped + validation; recall ingest idempotent + secret-gated +
  degrade-clean; matcher links a recall to a matching plan + fires app_notify; no match → no alert). 
  integration (nutrition_plans owner/family RLS + food_recalls classification + matches owner-scope proven
  as pawpi_app; any notifications CHECK widen; completeness guard green). mobile jest (nutrition card add/
  edit posts the right body; disclaimer present; recall alert renders + dismisses; empty states).

DO NOT: diagnose or prescribe a diet (non-diagnostic copy only); rebuild feeding routines (link, don't
duplicate); fabricate recalls or plans (real feed only; empty states); crash/block when the recall feed key
is unset (degrade cleanly); skip the family-access decision for nutrition_plans (match neighboring health
tables); gate on provider_type. Migrations hand-applied by Tats — flag in test-backlog ACTION 1; flag the
new recall-feed env key + external scheduler in the go-live actions (like CRON_SECRET in 2.17).

VERIFY: npm test + integration green; completeness guard green. PR body: nutrition_plans + food_recalls
(+ matches if added) with RLS proofs/classification, the owner nutrition CRUD, the secret-gated idempotent
recall ingest + matcher + best-effort notify, the mobile Nutrition card + recall alert, and the
non-diagnostic disclaimers. DEVICE: add a nutrition plan for a pet → it persists + shows the disclaimer +
links to feeding routines; with the recall feed configured + a seeded matching recall, an alert appears for
the right pet and dismisses; unconfigured feed shows no recalls (no crash); empty states when no plan.
```
