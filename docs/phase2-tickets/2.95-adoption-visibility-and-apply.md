## Context
`GET /api/adoption/listings` (`apps/web/src/app/api/adoption/listings/route.js`, the owner-facing adoption
browse) reads every PUBLISHED provider's AVAILABLE adoptable dog joined to the provider's primary location,
and — when the owner shares location — HARD-filters by a bounding box of `radius_km` (default **100**). A
prior fix rescued *coordless* shelters (they now show, sorted last) but left the radius box as a hard filter
for shelters that DO have a pin. The apply-to-adopt flow endpoint exists
(`apps/web/src/app/api/adoption/applications/route.js`). The mobile browse/detail live in
`apps/mobile/src/app/service/adoption.jsx`.

## Current issue (reported on device)
Northside Veterinary Clinic has the `adoption` capability set and a test dog listed, but as a pet owner you
see nothing to adopt or apply to. Two real causes:
1. **Located-but-far listings are dropped.** A shelter WITH a map pin more than `radius_km` (100km) from the
   browsing owner is hard-filtered out. With sparse early data this hides almost everything — distance
   should RANK results, not exclude them.
2. **Possibly not `status = 'available'`.** The browse requires `al.status = 'available'`; if the
   create-listing flow doesn't default a new listing to `available`, the dog is invisible from birth.

## Expected behavior
1. **Distance becomes a SORT, not a hard filter.** Remove the radius bounding-box exclusion from the default
   browse (keep the non-location filters — gender/size/age/etc. — as hard filters). Return all AVAILABLE
   dogs from PUBLISHED providers, sorted nearest-first when the owner shares location (coordless shelters
   last), featured/recent otherwise. If a radius filter is ever wanted, gate it behind an explicit opt-in
   param, off by default. A shelter across the country still appears, just ranked lower.
2. **New listings are visible by default.** Verify the provider create-listing flow saves
   `status = 'available'` (or make `available` the default) so a freshly created dog shows in browse
   immediately. Confirm Northside's test dog appears end-to-end.
3. **Apply to adopt works.** From the adoption detail screen a signed-in owner can submit an adoption
   application (existing `applications` endpoint); confirm the CTA is present and wired with a clear
   submitted/confirmation state. Guest → sign-in prompt.
4. Real data only; empty state only when there are genuinely no available dogs.

## Data / API rules
