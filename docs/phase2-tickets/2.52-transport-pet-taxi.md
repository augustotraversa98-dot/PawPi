# 2.52 — Transport / pet-taxi (new `transport` capability)

Read `00-README.md` (Wave 6 order + the ⚡ autonomy preamble) first. Web + mobile + migration. A pure
SPINE play: `transport` is already reserved in `ALLOWED_CAPABILITIES`. Reuse the unified provider spine,
generalized booking (2.4), payments (2.3), and chat (2.5). Do NOT rebuild onboarding / discovery /
profile / booking — extend them, exactly like grooming (2.6) / walking (2.7) / daycare (2.8) did.

```
ORIENTATION
Read ARCHITECTURE.md and supabase/SCHEMA_NOTES.md to get oriented, then this task. PawPi Expo mobile +
web API. Phase-2 ticket 2.52: a transport / pet-taxi service on the existing provider spine. Read
docs/phase2-tickets/00-README.md (CORE MODEL: gate on a CAPABILITY via requireProviderCapability, NEVER
on provider_type; shared conventions; the Wave 5 autonomy preamble applies).
AUTONOMY: don't ask; pick the sensible, on-brand option and proceed. CI green → auto squash-merge; red →
fix then merge. One fresh branch off origin/main: ticket/transport-pet-taxi.
Gates: npm test (web vitest + mobile jest); npm run test:integration (real-Postgres RLS).

CONTEXT
- The MULTI-CAPABILITY model (2.1): a business holds many capabilities; transport is one. `transport` is
  already in ALLOWED_CAPABILITIES (reserved). Discovery (?type=transport) must match providers HAVING the
  capability; a provider appears under every capability it holds. Capability ≠ data access (consent/RLS
  still gate pet data).
- Generalized booking (2.4) already handles cross-type bookings + the booking inbox + the web calendar
  (2.24). A transport request IS a booking — reuse it; add the transport-specific TRIP detail as a module
  table, the same way walk_sessions / grooming_sessions / sitting_visits hang off a booking.
- Payments (2.3) — checkout/charge/refund/payout is provider-agnostic; transport fares ride it (degrades
  cleanly to "payments not configured" until keys are set). Chat (2.5) — owner↔provider booking-scoped
  messaging is reused for "where are you / running late".
- Live GPS for an in-progress trip is OUT OF SCOPE here (it's the walker-GPS 2.7 pattern) — note it as a
  follow-up; v1 is request → schedule → assign driver → complete, with pickup/dropoff locations.

GOAL
An owner books a pet-taxi: pick a transport provider, request a trip (pickup + dropoff location, date/
time, pet + size/carrier needs, one-way/round-trip, notes), the provider confirms + assigns a driver
(staff member), the trip runs through statuses to completion, fare is charged via payments, and both sides
can chat. Provider sees transport trips on the dashboard (list + the 2.24 calendar) and the owner sees it
in the bookings/orders hub.

SCOPE
- Migration (next free ≥0052 — check supabase/migrations/ at build time; expected 0052):
  transport_trips (id, booking_id [FK to the generalized booking], provider_id, pet_id, owner_user_id,
  pickup_lat, pickup_lng, pickup_address text, dropoff_lat, dropoff_lng, dropoff_address text,
  scheduled_at timestamptz, trip_type text ['one_way','round_trip'], pet_size text nullable, carrier_needed
  bool default false, assigned_staff_id nullable [FK provider_staff], status text
  ['requested','confirmed','en_route','completed','cancelled'] default 'requested', fare_amount numeric
  nullable, notes text, created_at, updated_at). ENABLE+FORCE RLS, modeled on the existing session tables:
  the OWNER reads/creates own trips (booking-scoped); active provider STAFF of provider_id read + update
  (confirm/assign/advance status) via app_is_active_staff_of / app_is_provider_admin; the assigned driver
  reads their assigned trips. No cross-provider leakage; deny-by-default. REUSE the existing helpers
  (current_app_user_id, app_is_active_staff_of, app_provider_has_booking) — add a SECURITY DEFINER helper
  only if a predicate must read another RLS table (mind recursion). Harness proofs: owner manages own;
  provider staff of THIS provider read/update; other-provider staff + outsiders get zero; owner can't flip
  provider-only status fields they shouldn't. Flag in docs/test-backlog.md ACTION 1 (Tats hand-applies).
- Web (provider dashboard, reuse the shell): transport trips surface in the existing Bookings inbox + the
  2.24 Calendar (a trip is a booking) with confirm/assign-driver/advance-status/cancel actions; a trip
  detail shows pickup/dropoff (address + map), pet + size/carrier, fare + paid, assigned driver. Add a
  transport service to the provider's Services editor (capability-gated). NO new dashboard shell.
- Mobile (owner-facing): under Services, the transport/pet-taxi flow — discovery filtered to providers
  with the `transport` capability → provider storefront (reuse 2.22) → "Book transport" form (pickup +
  dropoff via the existing map picker from 2.43, date/time, pet, size/carrier, one-way/round-trip, notes)
  → booking created → pay via 2.3 → status visible in the bookings hub → chat via 2.5. Empty states only,
  no fake providers/trips.
- Tests: web vitest (trip create/confirm/assign/status owner-vs-staff scoping; capability gate; fare ties
  to the order; cross-provider isolation); integration (transport_trips RLS: owner manage, staff of the
  provider read/update, other-provider/outsider zero, owner can't set provider-only fields; completeness
  guard green); mobile jest (book-transport form posts the right body; discovery filters by capability;
  status renders; pay + chat entry points wired).

DO NOT: gate on provider_type (use requireProviderCapability('transport')); rebuild onboarding/discovery/
profile/booking/chat/payments (extend/reuse); build live GPS tracking (follow-up); expose another
provider's trips; show fake providers or trips; block booking if payments aren't configured (degrade
cleanly). Migrations hand-applied by Tats — flag in test-backlog ACTION 1.

VERIFY: npm test + integration green; completeness guard green. PR body: transport_trips + RLS proofs
(owner/staff/driver scoping), the capability-gated service, booking reuse (2.4) + calendar/inbox surfacing
(2.24), fare via payments (2.3), chat via 2.5. DEVICE: book a pet-taxi (pickup+dropoff on the map) → it
appears in the provider inbox/calendar → confirm + assign a driver → advance status → owner sees status +
can chat; paying degrades cleanly if keys aren't set; another provider never sees the trip.
```
