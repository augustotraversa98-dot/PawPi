## Context
A provider's adoptable dogs are currently shown ONLY in the standalone Adoption browse screen
(`apps/mobile/src/app/service/adoption.jsx`, reached from the More hub "Saved dogs", the Home tab, or the
Adoption category in Discover). They do NOT appear on the business's own storefront profile
(`apps/mobile/src/app/service/provider.jsx`): the storefront tabs (`apps/mobile/src/constants/storefrontTabs.js`)
are only services / items / posts / reviews / locations / about, and the public profile route returns no
adoption data. So a pet owner who opens a business like Northside — which has the `adoption` capability and
a listed dog — sees nothing to adopt there, which is confusing (it's the intuitive place to look).

The Adoption browse's card + detail + apply-to-adopt design is the one to reuse (the owner likes it). The
public browse endpoint `GET /api/adoption/listings` ALREADY supports filtering to a single provider via
`?provider_id=<id>` (verified in the route).

## Current issue
There's no way to see (or apply to adopt) a business's adoptable dogs from that business's profile.

## Expected behavior
1. Add an **"Adoption" tab** to the business storefront (`getStorefrontTabs`), shown ONLY when the provider
   has the `adoption` capability AND has ≥1 available listing — presence-aware, exactly like the other tabs
   (a provider with no available dogs shows no Adoption tab). Place it sensibly among the tabs (e.g. right
   after Services). i18n label `storefront.tabs.adoption` (EN "Adoption" / ES "Adopción").
2. The tab renders that provider's adoptable dogs by REUSING the SAME components/design as the
   `service/adoption.jsx` browse — the listing card grid, the listing detail, and the apply-to-adopt flow
   (including the "Application sent ✓" confirmation from 2.95). Do NOT hand-roll a parallel design; extract
   the browse's listing-card + detail + apply pieces into shared components if needed so both surfaces use
   one implementation.
3. Data: fetch this provider's listings via the existing `GET /api/adoption/listings?provider_id=<id>`
   (no location filter needed here — it's one business). Real data only; if somehow empty, the tab isn't
   shown (per #1).
4. Guests can view + open a listing; applying is gated to signed-in owners (prompt to sign in), consistent
   with the browse.

## Data / API rules
No migration. Reuse `GET /api/adoption/listings?provider_id=` (already supports the filter) and the existing
applications endpoint. No RLS change. If you instead choose to fold the listings into the public profile
payload, prove any new read in the integration harness — but the query-param reuse is preferred (smaller,
already proven).
