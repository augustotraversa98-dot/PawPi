# 2.15 — Mobile provider capability multi-select (onboarding)

Read `00-README.md` (⚠️ CORE MODEL — providers have MANY capabilities) + `../phase2-superapp-master-plan.md`
first. Depends on: 2.1 (`provider_capabilities` + `capabilities[]` already accepted server-side). This
is a **mobile-only, frontend-only** ticket — **no migration, no new web route**. It closes the gap where
the mobile business-onboarding form can only pick ONE business type, so a real "vet shop" can never be
created on a phone the way the multi-capability model intends.

> ⛔ **Downstream:** tickets **2.18 (telehealth)** and **2.20 (onboarding links)** are BLOCKED on this one
> — both edit the onboarding form this ticket builds (`vet-business-access.jsx`). Build 2.15 → 2.18 → 2.20
> **sequentially** (shared file; never two in parallel branches). Neither may start until 2.15 is merged
> to `origin/main`.

```
ORIENTATION
PawPi Expo mobile app. Phase-2 ticket 2.15: make mobile business onboarding MULTI-CAPABILITY. Read
docs/phase2-tickets/00-README.md (CORE MODEL) + the master plan.
Branch ticket/provider-capabilities-mobile off origin/main; squash-merge. NO migration, NO web change.
Gate: npm test (mobile jest). Confirm the mobile baseline first; after = baseline + net-new, nothing
pre-existing broken.

CONTEXT (read these before editing)
- apps/mobile/src/app/vet-business-access.jsx — the create-business form. TODAY it is a SINGLE-select
  `PROVIDER_TYPES` (only vet/walker/daycare/shop/groomer) and calls createProvider.mutateAsync({ name,
  provider_type, bio }). That is the whole gap: one type only, and missing sitter/trainer/adoption.
- apps/mobile/src/hooks/useProviders.js — useCreateProvider() posts to /api/providers. It must forward a
  capabilities[] array.
- apps/web/src/app/api/providers/route.js (POST) — ALREADY accepts an optional `capabilities` array,
  dedupes it, validates every entry against ALLOWED_CAPABILITIES (bad value → 400, not 500), inserts them
  into provider_capabilities (separate statement, RLS-safe), and returns provider.capabilities. provider_type
  is still REQUIRED. So the backend is ready — this ticket only feeds it the array.
- apps/web/src/app/api/utils/providerAuth.js — ALLOWED_CAPABILITIES is the source of truth.
- apps/web/src/app/provider/lib/providerTypes.js — the web onboarding's type list (keep mobile labels
  consistent with it).

GOAL: on mobile, a business owner selects ONE OR MORE capabilities (services they offer) when creating
their business, and those are persisted as provider_capabilities so the business surfaces under EVERY
service it offers in discovery — exactly like the web POST already supports.

SCOPE
- Convert the `PROVIDER_TYPES` single-select (radio) into a MULTI-select (checkbox/chip) capability
  picker. Offer ONLY capabilities that have a LIVE owner-facing service module (project rule: only feature
  live capabilities): vet, groomer, walker, daycare, sitter, trainer, shop, adoption. (Do NOT offer
  transport/pharmacy/telehealth — those service modules are not built yet; telehealth is added by its own
  ticket 2.18, which will append it here.) Each option keeps its emoji + human label.
- Require at least ONE capability selected (re-use the existing inline error pattern: "Please choose at
  least one service.").
- Submit shape: send `capabilities` = the full selected array AND `provider_type` = the FIRST/primary
  selected capability (provider_type stays required server-side and is now display-only per 2.1). Update
  useCreateProvider() to pass capabilities through. Keep name + optional bio unchanged.
- Success/already-onboarded/signed-out states, KeyboardAwareScrollView, COLORS, and the web-dashboard
  hand-off are UNCHANGED — only the type picker + the create payload change.
- (Optional, same ticket if cheap) a tiny "Selected: Vet, Shop" summary line under the picker for clarity.
  Skip if it bloats the diff.
- Tests (jest): the picker toggles multiple selections; submit with two capabilities posts
  capabilities:['vet','shop'] + provider_type:'vet'; submitting with none shows the validation error and
  does NOT call the mutation; useCreateProvider forwards capabilities in the request body.

DO NOT: add a migration; change the web POST (it already handles capabilities[]); offer non-live
capabilities; introduce fake providers; break the signed-out / already-onboarded / success states; gate
anything on provider_type (capability is the gate everywhere — 2.1).

VERIFY: npm test (mobile) green = baseline + net-new. PR body: the single→multi change, the live-only
capability set, the {capabilities[], provider_type:primary} payload, and that the web backend was already
ready (no server/migration change). Confirm origin/main. DEVICE PASS (add to docs/test-backlog.md): create
a business selecting two services (e.g. Vet + Shop) → it appears under BOTH Services screens in discovery;
selecting none is blocked.
```
