# 2.63 — App-wide keyboard UX: tap the field first, then the keyboard opens

Read `00-README.md` (Wave 6 order + the ⚡ autonomy preamble) first. Mobile only. NO migration. Touches
the Feed comment/bark composer + audits other inputs — sequence with the other Feed tickets.

```
ORIENTATION
Read ARCHITECTURE.md and supabase/SCHEMA_NOTES.md to get oriented, then this task. PawPi Expo mobile app.
Phase-2 ticket 2.63: stop inputs from grabbing focus + popping the keyboard automatically. The bark
(comments) field opens AND raises the keyboard the instant the view opens, which feels janky — the user
should TAP the field first, then the keyboard opens as a second step. Apply this consistently across the
app. Read docs/phase2-tickets/00-README.md (UI/UX principles; autonomy preamble).
AUTONOMY: don't ask; pick the sensible option and proceed. CI green → auto squash-merge; red → fix then
merge. One fresh branch off origin/main: ticket/keyboard-tap-to-focus.
Gates: npm test (mobile jest).

CONTEXT
- Opening barks/comments (components/Feed/BarkModal.jsx and the composer inside
  components/Feed/PostDetailModal.jsx) auto-focuses the TextInput (autoFocus / programmatic focus on
  mount), so the keyboard slides up at the same time the sheet animates in — not smooth.
- The keyboard-handling work already done (KeyboardAwareScrollView / KeyboardAvoidingAnimatedView, PR
  #37/#40) is about not COVERING inputs — keep all of that. This ticket is specifically about not
  auto-raising the keyboard before the user intends to type.
- This should be a consistent app-wide rule, not a one-off.

GOAL
Across the app, opening a screen/sheet/modal that contains a text field does NOT auto-open the keyboard.
The field is visible and tappable; the keyboard opens only when the user taps it. The bark/comments flow in
particular: the sheet/section opens smoothly, the input sits ready, the keyboard appears on tap. Existing
keyboard-avoidance (inputs never hidden behind the keyboard once focused) is preserved.

SCOPE
- Remove autoFocus / on-mount programmatic .focus() from the bark/comment composer (BarkModal.jsx +
  PostDetailModal.jsx comment input). The field renders unfocused; tapping it focuses + raises the
  keyboard.
- Audit the app for other auto-focusing inputs (grep autoFocus + on-mount inputRef.focus()) — search,
  onboarding, modals, etc. Remove auto-focus where it causes the same jank. NOTE: search (search.jsx) is a
  legitimate place to auto-focus (the user navigated there to type) — use judgment; the rule targets
  sheets/forms that pop the keyboard unexpectedly, not a dedicated search screen. Default to NO autoFocus
  unless auto-focus is clearly the desired UX.
- Keep KeyboardAwareScrollView / KeyboardAvoidingAnimatedView intact so a focused input is never covered.
- Tests: mobile jest (the bark composer mounts WITHOUT focus / does not auto-raise the keyboard; focusing
  on tap still works; existing keyboard-avoidance tests still pass).

DO NOT: remove the keyboard-avoidance wrappers (only the auto-focus); break the ability to type after
tapping; auto-focus sheets/forms; over-correct a dedicated search screen if auto-focus there is genuinely
better (judgment call, documented in the PR).

VERIFY: npm test green. PR body: the list of inputs de-auto-focused (where each was), the kept
keyboard-avoidance, and the search-screen judgment call. DEVICE: open barks/comments → the sheet animates
in smoothly with NO keyboard; tap the field → the keyboard opens and the field stays visible; same calm
behavior on other forms/modals; typing works normally after the tap.
```
