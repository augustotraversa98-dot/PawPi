# 2.29 — Internationalization: English + Spanish (device-locale)

Read `00-README.md` first. **Mobile-first, frontend-only, NO migration.** Independent — no blocker, but
**recommended LATER in the wave** (after the big provider/feed UI churn) so freshly-built screens are
translated once, not twice. Cross-cutting: introduces the i18n framework + Spanish, following the phone's
language.

```
ORIENTATION
PawPi Expo mobile. Phase-2 ticket 2.29: add internationalization with English + Spanish, defaulting to the
PHONE's language. Read docs/phase2-tickets/00-README.md.
Branch ticket/i18n-spanish off origin/main; squash-merge. NO migration. Gate: npm test (mobile jest).
Confirm the mobile baseline first.

HOW PHONE-LANGUAGE WORKS (the approach Tats asked about)
- expo-localization exposes the device locale (Localization.getLocales()). Pair it with react-i18next:
  English + Spanish string catalogs, default = the device language, fall back to English if it's neither,
  plus a MANUAL override in Settings. New screens use t("key") from then on.

CONTEXT (read before editing)
- There is NO i18n in the app today (confirmed). Strings are hard-coded across screens.
- Add deps: i18next + react-i18next + expo-localization. Confirm Expo SDK compatibility; note Expo Go vs
  dev-build behavior if relevant.
- apps/mobile/src/app/(tabs)/more/settings.jsx — where the manual language override lives.

GOAL: the app shows in Spanish on a Spanish phone and English otherwise, with a Settings toggle to force
English/Spanish. Core/high-traffic screens are translated; the framework + the t() pattern are in place so
the rest (and all NEW screens) get translated incrementally.

SCOPE
1. i18n setup: an i18n init module (i18next + react-i18next), two catalogs (en, es) under e.g.
   src/i18n/locales/, device-locale detection via expo-localization, fallback = en, and a persisted manual
   override (reuse the app's existing persisted-setting mechanism — same as pawpi:selectedPetId — key e.g.
   pawpi:locale). Provide the i18n provider at the app root.
2. Translate the CORE surfaces first (and provide the en+es strings): bottom nav labels, Feed/daily,
   Health (Today/Track/Insights/Vet Record top-level), Services + Pet Services grid, More menu, Settings,
   onboarding/auth, common buttons/empty states/errors. Use namespaced keys. Leave deeper/less-used
   screens for follow-up (track them in a short list in the PR), but the framework must cover the whole app
   so untranslated keys fall back to English cleanly (never a raw key on screen).
3. A language selector in Settings (System default / English / Español) that updates immediately + persists.
4. Date/number formatting: use locale-aware formatting where it already shows dates (don't regress the
   canonical YYYY-MM-DD storage — display only).
5. Tests: mobile jest — t() resolves en + es for a sample of keys; device-locale 'es' → Spanish, an
   unknown locale → English; the Settings override switches + persists; a missing key falls back to English
   (no raw key rendered).

DO NOT: add a backend/migration; machine-translate sloppily — Spanish should read naturally (neutral
LATAM-friendly Spanish, matching the warm tone); change stored data formats (display-only locale
formatting); leave any user-facing raw key. Don't try to translate EVERY string in one PR — cover core +
the framework, list the rest.

VERIFY: npm test (mobile) green (baseline + net-new). PR body: the i18n stack (i18next + react-i18next +
expo-localization), device-locale default + Settings override + persistence, the core screens translated,
the fallback behavior, and the follow-up list of screens still to translate. DEVICE PASS
(docs/test-backlog.md): Spanish phone → app in Spanish; Settings → switch to English/Español live; an
untranslated screen falls back to English, never shows a raw key.
```
