GOAL: a scheduled job re-buys each due shop subscription (product × quantity) through the SAME payment
layer as a normal shop order — creating an order, charging the owner's chosen rail (split → the shop is
paid), decrementing stock — then advances next_charge_at by the plan cadence. Safe to run repeatedly;
degrades cleanly when payments aren't configured.

SCOPE
1. Set the first charge date on subscribe (apps/web/src/app/api/shop/subscriptions/route.js POST): set
   next_charge_at = now() + the plan cadence on creation (the initial purchase already happened via the
   one-off checkout, so the FIRST auto-charge is one cadence later). Cadence map: weekly +7d, biweekly
   +14d, monthly +1 month, quarterly +3 months. Keep this map in a shared pure helper reused by the cron.
2. ⚙️ Migration 0039 — a SECURITY DEFINER enumerator `app_due_subscriptions()` returning the minimal due
   set (id, owner_user_id, provider_id, product_id, quantity, plan, next_charge_at) WHERE status='active'
   AND product_id IS NOT NULL AND next_charge_at <= now(). DEFINER (pinned search_path, GRANT EXECUTE to
   pawpi_app) because the cron has NO single owner identity and the scan crosses owners — mirror the
   0019/0023 helper pattern. It only READS subscriptions; no policy calls it back → no recursion. NO new
   table, so no RLS-table change; the completeness guard is unaffected (document this in the PR).
3. New protected route apps/web/src/app/api/payments/subscriptions/run/route.js (POST):
   - AUTH: a shared secret. Require header `x-cron-secret` === env CRON_SECRET (add to .env.example with
     a comment; if CRON_SECRET is unset, return 503 "scheduler not configured" — never run open). This
     route is NOT user-authed (it's machine-to-machine).
   - Enumerate via app_due_subscriptions(). For EACH due sub, in its OWN withTransaction + 
     setCurrentUserId(sub.owner_user_id) (so the order/order_items/payments INSERTs satisfy owner RLS)
     and its OWN try/catch:
       a. Re-validate the product under the owner's identity: active=true, NOT is_rx (Rx never
          auto-reorders — 2.11 rule), stock_qty >= quantity. Read price_cents server-side (NEVER trust a
          stored amount). Fail → skip (leave next_charge_at so it retries next run), record reason.
       b. Pick the rail: the provider's connected provider_payment_accounts (prefer 'mercadopago', else
          'binance'). None connected → skip as "provider not connected" (no crash).
       c. Build orders (kind='product', source_ref=`subscription:<sub.id>`, amount_cents, currency) +
          order_items (product_id, quantity, unit_cents=price_cents) — exactly like shop-checkout.
       d. createCheckout(order, { rail, idempotencyKey: `sub-<sub.id>-<period-boundary>` }). The period
          boundary (e.g. the next_charge_at date) makes a double-run in the same window a no-op via the
          payments ON CONFLICT(idempotency_key) — DO NOT double-charge.
       e. ONLY on a successful checkout creation, advance next_charge_at += cadence (the shared helper).
       f. Catch PaymentsNotConfiguredError + any per-sub error → skip that sub (do NOT advance, do NOT
          throw), log, continue the loop.
   - Return a summary { processed, charged, skipped, failed:[{subId, reason}] }. Always 200 on a
     completed run (per-sub failures are data, not a 500).
4. Tests:
   - vitest route (mock sql + createCheckout + app_due_subscriptions): due sub → order(kind='product')+
     items built with server-side price + createCheckout called with the period idempotency key +

     inactive / insufficient-stock → skipped; wrong/empty x-cron-secret → 503/401; a second run in the

   - vitest unit: the cadence helper (weekly/biweekly/monthly/quarterly advance correctly incl. month
