CONTEXT
- Payments (2.3) already created the money tables: payments, orders/order_items, payouts,
  provider_payment_accounts, transactions/ledger, subscriptions — all RLS'd (money = strictest). Money flows
  through them today; what's missing is a provider-facing place to SEE and reconcile it.
- The provider web dashboard (anything/apps/web/src/app/provider/) is the auth-gated shell with React Query
  + React Table + Tailwind + recharts; the bookings inbox + 2.24 calendar + storefront live here. Add a

- Provider scoping is by active provider_staff membership (app_is_active_staff_of / app_is_provider_admin);
  a staff member sees ONLY their provider's money. No cross-provider leakage.

GOAL
A provider (admin/owner staff) opens "Sales" in the dashboard and sees: revenue over time (recharts), a
transactions/orders ledger (date, type, customer/pet, gross, platform commission, net), payout history +
pending/next payout balance, and a reconciliation view that ties captured payments → orders → payouts so a
provider can confirm "what I earned vs what I've been paid." Read-only. Real data + empty states only.

SCOPE
- Web API (read-only): provider-scoped GET routes that aggregate the existing money tables for the caller's
  provider — e.g. /api/provider/[providerId]/sales (revenue series + totals by range), /payouts (payout
  rows + pending balance), /reconciliation (per-payout the orders/transactions it covers, plus any
  unreconciled/uncovered captured amounts). Resolve provider via active staff membership; reject non-staff.
  Reuse the existing sql.js + the payment/ledger schema; do NOT add new money tables or mutate money.
- RLS: if these reads only touch already-RLS'd money tables under the caller's provider scope, NO migration.
  ONLY if a reporting VIEW or a SECURITY DEFINER aggregate helper is genuinely needed, add it as the next
  free migration (check supabase/migrations/ at build time; would be ≥0056) with ENABLE+FORCE / DEFINER +
  EXECUTE-to-pawpi_app per the conventions, harness-proven, and flag it in test-backlog ACTION 1. Prefer NO
  migration — reuse the existing per-table RLS via membership-scoped queries.
- Web UI (reuse the shell): a "Sales" sidebar entry → tabs/sections: Revenue (recharts line/bar over a range
  selector), Ledger (React Table: date, type [booking fee / order / subscription / refund / payout],
  counterpart, gross, commission, net, status), Payouts (history + pending/next balance), Reconciliation
  (group transactions under their payout; flag anything captured-but-not-paid-out). Currency formatting
  consistent with the rest of the app; amounts are display-only. Empty states ("No sales yet", "No payouts
  yet"). Commission % comes from the platform config used by 2.3 — display it, don't recompute a new rule.
- Tests: web vitest (each read route is provider-staff-scoped: staff of the provider get their figures;
  non-staff/other-provider get 403/empty; totals/commission/net math is correct on a fixture; refunds reduce
  net; ranges filter). integration ONLY if a new view/DEFINER is added (prove it as pawpi_app + completeness
  guard green). No mobile work in this ticket.

new dashboard shell; leak another provider's money; invent commission logic (reuse 2.3's); show fake
figures (empty states); gate on provider_type. If a migration is unavoidable, flag it in test-backlog
