# 2.51 — Emergency mode + shareable/printable pet medical card

Read `00-README.md` (Wave 6 build order + the Wave 5 ⚡ autonomy preamble it points to) first.
Mobile + **public web page** + migration. Headline of Wave 6. EPIC trust feature. This is mostly an
ASSEMBLY of things that already exist (pet medical profile, the 2.28 share-frame, the consent engine,
2.48 Lost & Found's last-seen + microchip) — the only genuinely new piece is letting a NON-APP person
(an ER vet, or a stranger who finds the dog) view the card without logging in or installing anything.

```

Gates: npm test (web vitest + mobile jest); npm run test:integration (real-Postgres RLS).

CONTEXT
- The pet medical profile (pet_medical_profiles) + allergies / known conditions / current medications /
  vaccinations / microchip / primary vet + clinic phone / emergency contact already exist in the Vet
  Record and are owner-scoped (RLS R2c, proven in owner-private-rls.integration.test.ts). REUSE these
  sources — do NOT duplicate medical fields into a new table.
- The branded share-frame (2.28: react-native-view-shot + expo-sharing) renders an off-screen card to an
  image and opens the system share sheet. REUSE it for the in-app image/PDF share path.
- Lost & Found (2.48) already has lost_reports with last-seen lat/lng + status; the card should reflect
  "this pet is currently marked LOST" when an active lost_report exists, and surface the reward/contact.
- The notifications table (0044) + app_notify DEFINER helper exist if you want to ping the owner when their
  card is scanned (optional, best-effort, see SCOPE).
- Health positioning rule (PawPi_instructions.md): the app does NOT diagnose. The card ORGANIZES existing
  info for a real vet; it must carry the standard non-diagnostic framing and never infer/derive a
  diagnosis.

GOAL
A pet's Emergency Card: one screen that assembles the life-saving essentials — pet photo, name, species/
breed, age, blood type (if recorded), allergies, current medications, known conditions, microchip number,
spay/neuter status, primary vet + clinic phone, and the owner's emergency contact — plus a clear "currently
LOST" banner + reward + contact when an active lost_report exists. The owner can:
  (1) share it in-app as a branded image/PDF (reuse 2.28),
  (2) generate a REVOCABLE web link to the FULL card to hand to a vet (expires + instant revoke),
  (3) get a FIXED, PERMANENT tag QR with BASIC info to PRINT onto the dog's physical tag — anyone who
      finds the dog scans it and lands on a no-login, no-app-download public web page with the basics +
      a way to contact the owner.
Two public surfaces, deliberately different in what they expose:
  • TAG (fixed/permanent, printed on the collar): BASIC, always-safe info only — photo, name, breed,
    "this dog has a home", microchip #, lost/found status + reward, and an owner contact CHANNEL (a relay,
    not raw personal data unless the owner opts in). Permanent token so a printed tag never breaks.
  • MEDICAL LINK (revocable/expiring): the FULL emergency card incl. meds/allergies/conditions — for a vet.
    Owner creates on demand, sets expiry, can revoke instantly.

SCOPE
- Migration (next free ≥0051 — check supabase/migrations/ at build time; expected 0051):
  pet_emergency_cards (id, pet_id UNIQUE, owner_user_id, tag_token text UNIQUE [stable/permanent — the
  printed QR], show_medical_on_tag bool default false, contact_mode text ['relay','phone','email','none']
  default 'relay', contact_value text nullable, blood_type text nullable, extra_notes text nullable,
  active bool default true, created_at, updated_at) — one row per pet, lazily created on first open.
  pet_emergency_share_links (id, pet_id, owner_user_id, token text UNIQUE, scope text ['full','basic']
  default 'full', expires_at timestamptz nullable, revoked_at timestamptz nullable, created_at) — the
  revocable vet links.
  ENABLE+FORCE RLS on BOTH, OWNER-SCOPED for all owner CRUD (owner manages own; others zero direct access).
  THE PUBLIC READ IS NOT AN RLS HOLE — it goes through SECURITY DEFINER functions ONLY (pinned
  search_path, GRANT EXECUTE to pawpi_app), never a broad SELECT policy:
    • app_emergency_card_by_tag(tag_token text) → returns ONLY the BASIC tag fields (+ medical fields IFF
      show_medical_on_tag) for an ACTIVE card, joining the live medical sources read-only; no owner row
      ids, no raw owner contact unless contact_mode permits.
    • app_emergency_card_by_link(token text) → returns the scoped card (full|basic) for a link that is
      non-revoked AND non-expired; otherwise zero rows.
  Both functions are the SOLE path public web uses; the tables themselves stay deny-by-default to
  pawpi_app. Money/medical = strictest — leak NOTHING beyond the function's whitelisted columns. Harness
  proofs: owner manages own card/links; another user gets zero on the tables directly; the tag function
  returns basic-only (medical only when toggled); the link function returns full for a valid token and
  ZERO for revoked/expired; a non-owner cannot create/revoke another pet's links. Flag the migration in
  docs/test-backlog.md ACTION 1 (Tats hand-applies).
- Web (PUBLIC, no auth, no app-install wall): two server-rendered read-only pages that call the DEFINER
  functions —
    • /p/tag/[tagToken] — the permanent tag page (basic; medical only if the owner enabled it). Mobile-
      first, prints clean. A clear "Contact owner" affordance per contact_mode (relay form → app_notify
      to owner / tel: / mailto: / none). A "found this pet?" → report-a-sighting hand-off if a lost_report
      is active (reuse 2.48). NO login prompt, NO "download the app" gate.
    • /p/card/[linkToken] — the revocable full card for vets; shows "link expired/revoked" cleanly when
      invalid.
  Keep these OUTSIDE the auth-gated provider shell (they're public). Strip anything not whitelisted by the
  function. Generate the QR for the tag page (a small, dependency-light QR lib or an inline SVG generator).
- Mobile (owner-facing, in the Vet Record / pet area):
    • "Emergency Card" entry → the assembled card (live from the medical sources + lost status).
    • "Share card" → reuse the 2.28 branded capture → image/PDF to the system share sheet.
    • "Get tag QR" → shows the printable tag QR + the /p/tag/ URL + a toggle "show medical info on the
      public tag" (default OFF) + the contact-mode chooser (relay default).
    • "Share with a vet" → create a revocable link (set expiry: 24h / 7d / no-expiry) → share URL;
      a list of active links with instant "Revoke".
    • If the pet has an active lost_report, the card shows the LOST banner + reward + sighting hand-off.
  Empty/missing medical fields render as clean "Not recorded" rows (NO fake data) — an incomplete card is
  fine and still useful.
- Notifications (optional, best-effort, never blocks): when a tag/link page is opened, you MAY app_notify
  the owner ("Your emergency tag for {pet} was just viewed"). If you add a notification type, widen the
  0044 notifications_type_check additively (drop+re-add) — same pattern as 2.48's 'lost_alert'. A notify
  failure must never break the public page.
- Tests: web vitest (DEFINER tag fn returns basic-only / medical-when-toggled / nothing for inactive;
  link fn returns full for valid + nothing for revoked/expired; owner CRUD scoping; the public pages
  render without auth and strip non-whitelisted fields); integration (both tables owner-scoped + deny-by-
  default; the two DEFINER functions enforce active/expiry/revoke + scope; non-owner can't create/revoke;
  completeness guard green); mobile jest (card assembles from sources + "Not recorded" empties; share
  reuses 2.28; tag toggle + contact mode persist; create + revoke link; LOST banner when active).

DO NOT: put a broad public SELECT policy on the card/link tables (public reads go through the DEFINER fns
ONLY); expose the full medical card on the FIXED tag by default (basic only unless the owner opts in);
leak owner raw contact unless contact_mode permits; gate the public pages behind login or an app-install
wall; diagnose or derive any medical conclusion (organize existing fields only, keep the non-diagnostic
framing); show fake/sample medical data; let a revoked/expired link still resolve. Migrations hand-applied
by Tats — flag in test-backlog ACTION 1.

VERIFY: npm test + integration green; completeness guard green. PR body: the two tables + their OWNER-only
RLS + the two SECURITY DEFINER public-read functions (basic vs full, active/expiry/revoke enforced) with
harness proofs; the two public pages (/p/tag/[token] permanent, /p/card/[token] revocable) rendering with
no auth; the printable tag QR; the in-app share reusing 2.28; the LOST banner integration. DEVICE/BROWSER:
open the in-app card → share as image; print/scan the tag QR → it opens the public basic page on a phone
browser with NO login (toggle medical on → it appears; off → it doesn't); create a vet link → open in a
browser → full card; revoke it → the same URL now says expired/revoked; mark the pet lost (2.48) → the
card + tag show the LOST banner + sighting hand-off.
```
