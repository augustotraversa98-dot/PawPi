# 2.22 — Provider storefront profile + posts (the "store")

Read `00-README.md` + `../phase2-superapp-master-plan.md` (§4 dog-profile reuse) first. Depends on: 2.1,
2.2 (reviews), the shop (2.11) for items, services (spine). **Recommended AFTER 2.23 (service/product
images)** so the storefront renders rich media — not a hard blocker (it degrades to text + existing
product images). ⛔ **SHARED FILE: build AFTER 2.20** — both this ticket and 2.20 extend the public
provider route `apps/web/src/app/api/providers/public/[slug]/route.js` (2.20 adds the links, this adds
posts/cover/services/items). Don't run them as parallel branches; sequence 2.20 → (2.23) → 2.22. Adds
migration **0042** (`provider_posts` + a `providers.cover_image_url`).

```
ORIENTATION
PawPi web (provider compose) + Expo mobile (owner view). Phase-2 ticket 2.22: turn the public provider
profile into a STOREFRONT — "entering the store" (Shopify-like): services, items, reviews, info, links,
and the provider's POSTS. Read docs/phase2-tickets/00-README.md + master plan §4.
Branch ticket/provider-storefront off origin/main; squash-merge.
⚙️ NEW MIGRATION 0042 (provider_posts table + providers.cover_image_url). Gates: npm test (web vitest +
mobile jest) + npm run test:integration (RLS proofs for provider_posts + guard). Confirm baselines first.

CONTEXT (read before editing)
- apps/web/src/app/api/providers/public/[slug]/route.js — the existing public profile (published provider
  + locations + active services + capabilities). This is the storefront's backbone — EXTEND it, don't fork.
- apps/mobile/src/app/(tabs)/more/provider.jsx (+ components/Providers/*) — the owner-facing provider
  profile screen. This becomes the storefront view.
- provider_reviews (2.2) — rating + reviews already surface; include them in the storefront.
- shop_products (2.11, image_urls[]) = the store ITEMS; provider_services = the service menu. Show both.
- Supabase Storage upload path (reused everywhere) for post images + the cover image.

GOAL: an owner opening a provider sees a rich storefront — cover image + logo, name/bio/links, star
rating + reviews, the service menu (with prices), the item catalog (shop products), and a feed of the
provider's POSTS (announcements/photos). The provider composes posts + sets the cover from the web
dashboard. Everything real, empty states where there's nothing — no fake content.

SCOPE
1. Migration 0042 — provider_posts (id, provider_id, author_user_id, body text, image_urls text[],
   created_at, updated_at, deleted_at) + providers.cover_image_url (additive). ENABLE+FORCE RLS:
   provider_posts are PUBLIC-READ for a PUBLISHED provider (any authed user — discovery/storefront), and
   WRITE by active staff of that provider (mirror the published-read + staff-write pattern from
   provider_services 2.x / the shop). Cover image rides providers' existing RLS. Harness proofs (published
   posts readable by any authed; a non-staff user can't write; another provider's staff can't write) +
   completeness guard.
2. Web (provider dashboard): a "Storefront"/"Posts" section — compose a post (text + images via Storage),
   list/delete own posts, set the cover image. Reuse the dashboard shell + React Query.
3. Web public route: extend public/[slug] to also return cover_image_url, the provider's posts
   (paginated, newest first, like /api/posts), the service menu, and the item catalog summary — all
   published/public fields only (NO staff/owner/payment/medical data; assert in tests).
4. Mobile storefront (more/provider.jsx): render the storefront sections — cover+logo header, info+links,
   rating+reviews, Services menu, Items (shop products → tap into the shop catalog/checkout that already
   exists), and the Posts feed. Empty states everywhere. "Book"/"Message"/"Shop" CTAs reuse the existing
   booking / chat / shop flows (do not rebuild them).
5. Tests: vitest (public route returns posts/cover/services/items, only public fields; pagination);
   integration (provider_posts RLS proofs + guard); mobile jest (storefront renders each section + empty
   states; CTAs route to the existing flows).

DO NOT: rebuild booking/chat/shop/reviews — link into them; expose private data on the public storefront;
add fake posts/items; fork the public profile route (extend it). Keep the warm existing design.

VERIFY: npm test (web+mobile) + integration green (baseline + net-new). PR body: provider_posts + cover
(0042) + RLS proofs, the extended public storefront route, the web composer, the mobile storefront reusing
existing CTAs. ⚙️ FLAG FOR TATS: apply 0042. DEVICE PASS: open a provider → storefront shows info/rating/
services/items/posts; provider posts from the dashboard → appears on the storefront; empty sections show
empty states.
```
