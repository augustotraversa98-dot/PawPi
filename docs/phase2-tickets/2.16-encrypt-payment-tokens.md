# 2.16 — Encrypt provider payment tokens at rest

Read `00-README.md` + `../phase2-superapp-master-plan.md` (§3 payments) first. Depends on: 2.3 (payments
foundation). This closes the explicit follow-up flagged in `0029_payments_foundation.sql` (the
`provider_payment_accounts.access_token` comment: *"Encrypted-at-rest is a prod follow-up"*) and in the
roadmap (*"encrypt provider OAuth tokens at rest"*). **Pre-launch security.** Backend-only, web app only.

> ⛔ **Downstream:** ticket **2.17 (subscription auto-charge cron) is BLOCKED on this one** — it reads
> provider tokens through the decryption seam this ticket adds. 2.17 must not start until 2.16 is merged
> to `origin/main`.

```
ORIENTATION
PawPi web API. Phase-2 ticket 2.16: encrypt the provider payment OAuth tokens AT REST. Read
docs/phase2-tickets/00-README.md + master plan §3.
Branch ticket/encrypt-payment-tokens off origin/main; squash-merge.

WRITE/READ shape of provider_payment_accounts, not its RLS). Confirm both baselines first.
NO migration needed — ciphertext is stored as text in the EXISTING text columns (see DO NOT).

CONTEXT (read before editing)
- supabase/migrations/0029_payments_foundation.sql — provider_payment_accounts (provider-admin-only RLS,
  no owner branch). access_token + refresh_token are the secrets; account_ref + meta are public-ish.
  Binance stores ONLY account_ref (a public handle) — no secret — so Binance needs no change.
- apps/web/src/app/api/providers/[id]/payment-accounts/mercadopago/callback/route.js — the ONLY place a
  secret token is WRITTEN (INSERT ... access_token, refresh_token, meta ... ON CONFLICT DO UPDATE). This
  is where encryption-on-write goes.
- apps/web/src/app/api/utils/payments/index.js — loadProviderAccount(providerId, rail) is the single
  READ seam: createCheckout/getStatus/refund all call it, then pass the row to the adapter. Decryption-
  on-read belongs here so the row handed to the adapter still carries PLAINTEXT account.access_token.
- apps/web/src/app/api/utils/payments/mercadopago.js — the adapter reads account.access_token verbatim
  (Bearer auth). It must stay unchanged: it always sees decrypted tokens.

GOAL: provider MercadoPago OAuth tokens are encrypted before they touch the database and decrypted only
in-process when a charge/refund needs them. A DB dump (or anyone with raw table access) never sees a
usable token. No behavior change to checkout/refund/payout.

SCOPE
- New util apps/web/src/app/api/utils/payments/tokenCrypto.js (pure, unit-testable):
  encryptToken(plaintext) → string, decryptToken(stored) → plaintext|null.
  * AES-256-GCM via Node's built-in `crypto` (no new dep). Key from env PAYMENTS_TOKEN_KEY (a 32-byte
    key, base64 or hex — document the format in .env.example). Random IV per encryption; store
    iv+authTag+ciphertext together.
  * VERSION-PREFIX the output (e.g. "enc:v1:<base64>") so reads can tell ciphertext from any legacy
    plaintext and future key rotation is possible.
  * decryptToken: "enc:v1:" prefix → decrypt; no prefix → return as-is (legacy/plaintext passthrough,
    so the harness + any pre-existing row never breaks). null/undefined → null.
  * Key handling: if PAYMENTS_TOKEN_KEY is MISSING, encryptToken THROWS a clear config error (refuse to
    store a secret in plaintext) — but this only fires inside the MP connect flow, which itself already
    requires MP keys, so it can never break unconfigured installs. decryptToken with a missing key on a
    plaintext row still passes through.
- Wire encryptToken() into the mercadopago/callback write (access_token + refresh_token only; leave
  account_ref + meta as-is — meta must NOT carry secrets; if it currently does, move them or note it).
- Wire decryptToken() into loadProviderAccount() in payments/index.js so every consumer (adapter,
  refund, getStatus, payout) receives plaintext. This is the ONLY decrypt point.
- .env.example: add PAYMENTS_TOKEN_KEY with a comment on generating one (e.g. openssl rand). NEVER a
  real value.
- Tests:
  * vitest unit (tokenCrypto): round-trip encrypt→decrypt; ciphertext != plaintext + carries the version
    prefix; legacy plaintext passes through unchanged; tampered ciphertext fails (GCM auth) cleanly;
    missing key → encrypt throws, decrypt-plaintext passes.
  * vitest route: mock the callback's sql and assert the value bound for access_token starts with
    "enc:v1:" (a secret is never persisted in clear); loadProviderAccount returns a decrypted token to
    the adapter.
  * integration harness: provider_payment_accounts RLS proofs stay green (provider-admin-only unchanged).

DO NOT: add a migration or new columns — store ciphertext in the existing access_token/refresh_token
TEXT columns (base64 ciphertext fits). Touch the adapters' token usage. Change RLS on
provider_payment_accounts (it is already provider-admin-only — encryption is defense-in-depth on top).
Log or return a token anywhere. Encrypt account_ref (it is a public payout target). Commit a real key.

VERIFY: npm test + npm run test:integration green (baseline + net-new). PR body: AES-256-GCM helper,
encrypt-on-write at the MP callback, single decrypt-on-read in loadProviderAccount, version-prefix +
legacy passthrough, no migration, RLS unchanged. Flag for Tats: set PAYMENTS_TOKEN_KEY in the web .env
BEFORE the first real provider connects (add it to the go-live checklist alongside the pawpi_app
password). No on-device check (backend-only).
```
