# 2.12 — Adoption module ("adoption place" + its dogs + application workflow)

Read `00-README.md` + `../phase2-superapp-master-plan.md` §4 first. Depends on: 2.1 (capability), 2.3
(fees/donations), 2.5 (chat). Capability = `adoption`.

```
ORIENTATION
PawPi web API + mobile. Phase-2 ticket 2.12: the ADOPTION module — a shelter/rescue ("adoption place")
lists its adoptable dogs IN THE EXISTING DOG-PROFILE FORMAT; owners browse, apply, chat, pay an
adoption fee/donate, and the adopted dog flows into the owner's normal pet experience. Read
docs/phase2-tickets/00-README.md + master plan §4. Gate with requireProviderCapability(
providerId,'adoption'). The "adoption place" = a provider (reuse onboarding/profile/locations/staff).
REUSE the existing pet/dog-profile UI to render listings ("place all their dogs in the format it
currently is"). Read the pet/dog-profile components + the pets schema so listings reuse them.
Branch ticket/adoption off origin/main; squash-merge; migration for adoptable listings + applications.
Gates: npm test + npm run test:integration.

GOAL: shelters list adoptable dogs (rich dog profiles); owners discover places + dogs, favorite, apply,
chat, pay fee/donate; on approval the dog becomes the adopter's pet.

SCOPE
- The "adoption place" = provider with capability='adoption' (org profile via the spine).
- Adoptable dogs: model so they render in the existing dog-profile format AND are owned by the shelter
  provider. Option (document choice): pets rows owned by the shelter (owner_user_id = shelter's profile
  or a shelter-link) with adoption fields, OR an adoptable_pets table that reuses the pet-profile
  render. Fields: name/breed/age/gender/size/photos/video/story + good_with_kids/cats/dogs, energy,
  vaccination status (may read pet_vaccinations), adoption_fee, status (available/pending/adopted).
  RLS: a published place's available listings readable by any authed (discovery); shelter-staff write.
- Applications: adoption_applications table (listing_id, applicant_owner_user_id, answers, status
  [submitted/under_review/approved/declined], created_at). Owner submits; shelter staff review
  (dashboard). Chat (2.5) between applicant + shelter. RLS: applicant sees own; shelter staff see
  their place's applications. Harness proofs.
- Fee + donations via 2.3: adoption fee on approval (orders kind='adoption_fee'), donations to a place
  (kind='donation', split → place payout).
- On APPROVAL: transfer/create the pet under the adopter (a new pets row owned by the adopter, copying
  the profile) so the dog enters the owner's normal health/social/services experience; mark listing
  adopted. Document the transfer mechanics.
- mobile: owner — browse adoption places + their dogs (dog-profile cards), favorite, apply, chat, pay;
  shelter (web) — manage listings + review applications. Discovery ?type=adoption under Services →
  Adoption. (This replaces the old mock Adoption screen.)
- Tests: capability gate; listing CRUD + public discovery; application submit/review; fee/donation via
  2.3; approval → adopter pet creation; RLS on listings + applications.

DO NOT: bypass capability gate; expose applications across users; rebuild the dog-profile UI (reuse it);
duplicate payments. No fake listings.

VERIFY: npm test + integration green. PR body: the place+listings(dog-profile-format) model,
application workflow, fee/donation, approval→pet-transfer, RLS. Migration hand-applied after merge.
Confirm origin/main.

FOLLOW-UP (note): foster workflow; "urgent"/featured listings; multi-pet bulk import for shelters.
```
