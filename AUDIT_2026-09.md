# PawPi — Full-stack audit, September 2026

**Date:** 2026-09-09 · **Base:** `main` @ `69f4b54c` · **Scope:** mobile (`anything/apps/mobile`), web + API (`anything/apps/web`), database (`supabase/migrations` + live Supabase advisors, read-only).
**Baseline:** web vitest 284 files / 2180 tests green · mobile jest 263 suites / 2051 tests green · Supabase security advisor: 1 warning · performance advisor: 4 lint classes (below).

**Method.** Phase 0 read the prior work (`anything/AUDIT_REPORT.md`, `SECURITY_FIXES_PROMPT.md` + `docs/night-run/2026-08-21/SECURITY_FIXES.md`, `docs/rls-hardening.md`, `anything/PAYMENTS_DIAGNOSIS.md`, the RLS integration suite). Everything below is **net-new**; already-known items (SSRF, upload validation, rate limits, checkout `amount_cents`, `expo-web-success` origin, emergency-tag projection, owner-deletes-vet-notes, RLS R0–R2g) are not repeated. Live DB was inspected read-only via the Supabase MCP (`get_advisors`, `pg_policy`, `pg_roles`, `pg_stat_statements`, `pg_stat_user_tables`). No SQL was applied; no production data touched.

**Headline.** The route layer and RLS are in good shape: all 271 API route files were triaged and **no cross-user or cross-pet data leak was found at the application layer**; prod connects as `pawpi_app` with RLS forced on 130/135 public tables. The real risks are (1) one **latent** database-privilege exposure that is one leaked key away from a full dump, (2) the **"endless loading" class** that got build 16 rejected — a root cause exists in the shared fetch layer and one post-login screen, and (3) a cluster of **Argentina-timezone day bugs** that make the Care Ring, daily moment and reminders disagree after 21:00 local time.

## Phase 1 — Data leaks / security

### A-01 · P0 (latent) · Supabase `anon`/`authenticated` roles have full table + function privileges — ⚠️ HELD
**Location.** Live DB (`information_schema.role_table_grants`, `has_function_privilege`). Supabase's default `GRANT ALL ON ALL TABLES IN SCHEMA public TO anon, authenticated` was never revoked; the app never uses PostgREST (it connects directly as `pawpi_app`), but PostgREST 14.5 is running and `public` is an exposed schema.
**Impact.** RLS is forced on 130 tables, so `anon` reads zero rows there. But the five RLS-exempt identity tables (`auth_users` — password hashes —, `auth_accounts`, `auth_sessions`, `auth_verification_token`, `user_profiles`) are fully readable and writable by `anon`, and all 92 DEFINER functions are executable (`app_ban_user` checks `app_is_admin()` so it is safe; `app_notify(recipient, actor, …)`, `app_grant_walk_credits(order_id)`, `ingest_food_recall(...)`, `app_record_consent(auth_user_id, …)`, `app_create_password_reset_token(auth_user_id, …)` take their subject as a parameter and would run for anyone). The only thing standing between the internet and this is the project's anon key — which is absent from the repo and the mobile bundle today, but is by Supabase's own model a "publishable" value.
**Repro (do not run against prod).** `curl "$SUPABASE_URL/rest/v1/auth_users?select=email,password_hash" -H "apikey: <anon>"` → 200 with rows.
**Fix (migration `0126`, hand-applied after review — it revokes nothing the app uses).**
```sql
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM anon, authenticated;
```
Belt-and-braces: in the Supabase dashboard remove `public` from *Settings → API → Exposed schemas* (the app does not use the Data API). The demo-seed script and my verification curls use `service_role`, which is unaffected. Verification after apply: `select count(*) from information_schema.role_table_grants where grantee in ('anon','authenticated') and table_schema='public'` → 0.

### A-04 · P1 · Medical files in the public `media` bucket — ⚠️ HELD (storage change)
**Location.** `anything/apps/web/src/app/api/upload/route.js:11-14,52,78` (single bucket, `uploads/<uuidv4>.<ext>`, returns `/storage/v1/object/public/media/...`); callers `AddDocumentModal.jsx:234` (vet PDFs → `vet_record_documents.file_url`), `PhotoCheckCaptureModal.jsx:237`, `GeneralCheckModal`, `PooTrackerModal`, `VomitTrackerModal:218`, `chat.jsx:85`, `provider-chat.jsx:99`, `vet-business-access.jsx:292`. Live bucket: `public=true, file_size_limit=null, allowed_mime_types=null`.
**Impact.** A URL, once minted, is a permanent unauthenticated credential to a medical document; it survives care-grant revocation, caregiver removal, chat deletion and account deletion, and it is written to client logs (`useUpload.js:150`). Paths have 122 bits of entropy and listing is closed, so this is a *bearer-URL* problem, not an enumeration one.
**Fix.** Second private bucket (`media-private`) for the six medical/chat callers; server-side owner prefix (`pets/<petId>/...`); serve through `GET /api/media/[key]` (auth + owner/family/`assertCareAccess('medical_read')`) that streams with the service key or 302s to a 60 s signed URL; store the object key, not the URL. Meanwhile set `file_size_limit` + `allowed_mime_types` on the bucket to mirror `uploadValidation.js`. Migration of existing rows is a data change → review.

### A-05 · P1 · 30-day JWT with no revocation — ⚠️ HELD (auth core)
**Location.** `anything/apps/web/__create/index.ts:174` (`strategy:'jwt'`, default 30-day `maxAge`); `api/auth/token/route.js:11-36` hands the raw JWT to mobile; `mobile/src/__create/fetch.ts:93-102` replays it with no refresh; `useAuth.js:54` `signOut` is local-only; `account/reset-password/route.js:23` clears `auth_sessions`, which the JWT strategy never reads.
**Repro.** Log in on device A, capture the bearer, reset the password on web, replay → 200.
**Fix.** `session.maxAge` 7 d; `auth_users.token_invalidated_at` checked in a Hono middleware on `/api/*` (`iat < token_invalidated_at` → 401), bumped on password reset / sign-out-everywhere / deletion; pairs with A-07 on the client. Needs an on-device login test before merge.

## Phase 2 — Dead ends & hangs

### A-02 · P0 · No fetch timeout → permanent spinner
**Location.** `anything/apps/mobile/src/__create/fetch.ts:47-110` forwards `init` untouched (no `AbortSignal`); `src/utils/queryClient.js` (`retry: 1` never fires because the promise never rejects; `cacheTime` is a v4 name ignored by v5). Every React-Query `queryFn` uses this `fetch`. The only bounded request in the app is the boot pets fetch (`app/index.jsx:46`, 12 s).
**Trigger.** Any data screen → captive Wi-Fi / half-open TCP / backend cold start → `isLoading` forever; pull-to-refresh is usually hidden behind the spinner branch. This is the build-16 rejection profile.
**Fix (PR-1, ~15 lines).** For first-party URLs with no `init.signal`, attach a 15 s `AbortSignal` (controller + `setTimeout`, cleared in `finally`); rename `cacheTime` → `gcTime`; add `retryDelay`. Every hang then falls into the screens' existing `isError` branches. Unit test: a never-resolving fetch rejects with `AbortError` after the deadline.

### A-03 · P0 · Post-login screen can spin forever / mis-route
**Location.** `anything/apps/mobile/src/app/auth/expo-web-success.jsx:57-121`, reached from `AuthWebView.jsx:26` on every sign-in.
**Trigger.** Welcome → Sign in → "Setting up your account…": if `/api/user-profile` or `/api/pets` stalls → spinner forever; if `/api/pets` 5xx → `replace("/onboarding-photo")` (the duplicate-pet path `determinePetsRoute` exists to prevent); business/staff account with no pets → pet onboarding (never consults `/api/providers`); generic error → onboarding after 1.5 s.
**Fix (PR-2).** After the token is stored, `router.replace("/")` and let `app/index.jsx` (12 s abort, retry screen, role-aware `determinePetsRoute`) decide; delete the duplicated logic.

### A-06 · P1 · Offline renders as "empty"
`networkMode:'online'` leaves offline queries `pending/paused` (`isLoading=false`, `data=undefined`) so every ternary falls into its empty branch ("No shops yet", "No messages"); RN never tells React Query it is offline (`onlineManager` unwired). Fix (PR-4): `onlineManager.setEventListener` with `@react-native-community/netinfo` (already a dependency) in `_layout.jsx`, plus a one-line offline banner, plus `focusManager` wiring (also fixes A-16).

### A-07 · P1 · No 401 handling mid-session
`fetch.ts` never inspects status. Fix (PR-5): on 401 from an API URL → `useAuthStore.getState().setAuth(null)` (guarded) + `router.replace('/welcome')`.

### A-08 · P1 · Notification taps
`src/utils/handleNotificationTap.js:14` pushes `/(tabs)/health` unconditionally, every typed case is a comment-only `break`, and `default` pushes again (duplicate stack entry). `utils/notifications.js:448` `addNotificationResponseListener` has zero callers → OS push taps (BN2 server pushes carry `data.route`) never deep-link. Fix (PR-6): route per type (`/(tabs)/health?section=…` already exists), register the response listener + `getLastNotificationResponseAsync()` in `_layout.jsx` with a whitelist of known routes.

### A-09 · P1 · `pet-profile.jsx:52-72` ignores `isError`; `notifications.jsx:469-494` has no loading/error gate. Fix: reuse the `EmptyState` + `common.retry` pattern from `service/place.jsx:142-155` / `service/shop.jsx`.

### A-33 · P3 · `SettingsTab.jsx:95-100` "Quiet hours" coming-soon Alert (hide behind a flag like `SHOW_NUTRITION`); loading-without-error screens: `service/provider-post.jsx`, `service/place.jsx` (no retry), `events.jsx`, `follows.jsx`, `vet-business-access.jsx`, `lost-found.jsx`, `(tabs)/more/profile.jsx`; `telehealth-call.jsx` overlay needs a 15 s fallback.

### A-18 · P1 · Server-side hang budget — ⚠️ role setting
`pawpi_app` has `rolconfig = null` (no `statement_timeout`; Supabase's own `authenticated` role has 8 s). `utils/sql.js` uses postgres.js defaults (`max: 10`, `connect_timeout: 30`) and `withRequestContext` holds a connection for the whole request. Twelve routes do external network I/O inside that transaction (`payments/checkout`, `payments/[id]/refund`, `pets/[id]/shop-checkout`, `pets/[id]/walk-package-checkout`, `pets/[id]/daycare-stays`, `providers/[id]/bookings/[appointmentId]`, `account/forgot-password`, the three cron runners, `upload`, `internal/grafana-alert`). A slow MercadoPago/Expo push/Resend call pins a connection; ten of them and every other request queues behind `postgres()`'s wait list → app-wide spinner. Fix: `ALTER ROLE pawpi_app SET statement_timeout = '15s'` (review: long seeds run as `postgres`, unaffected) + `idle_in_transaction_session_timeout = '30s'`; in code, add `AbortSignal.timeout` to the MercadoPago/push/e-mail fetches (most already have one — verify) and move post-commit side effects (push, e-mail) after the transaction where the route shape allows.

## Phase 3 — Speed

### A-14 · P1 · Discovery endpoints unbounded
`providers/discover/route.js` and `services/discover/route.js` have no `LIMIT`/`OFFSET` (only the `LATERAL … LIMIT 1` location join). `pg_stat_statements`: the providers query averages 100.7 ms and returns 130,931 rows over 95 calls (≈1,378 rows per call) with three correlated subqueries per row (`avg_rating`, `review_count`, `array_agg(capability)`); `providers` shows 30,219 sequential scans on 3,633 rows. The mobile side now virtualizes (#526) but still downloads and parses the whole directory. Fix (PR): `?limit=` (default 60, max 200) + `?cursor`/`offset` on both routes, wired through `useDiscoverProviders`/`useServicesDiscover` as `useInfiniteQuery`; when `lat/lng` are absent, still cap.
